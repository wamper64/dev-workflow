# 本轮模块验收收口、retro与下一轮决策

## 输入

- 本轮计划、已批准Spec/Tickets及模块详细设计。
- `docs/output/06-模块迭代/<模块>/实现与自动验证记录.md`、`代码审查记录.md`和实际Git提交/集成分支。
- `docs/output/06-模块迭代/<模块>/人工测试用例与结果.md` 中实际**人工**填写的用例结果、执行人、日期及证据。
- 若发生Bug，其官方 `diagnosing-bugs` 修复与原用例人工复测证据。
- **本轮真实AI编码会话/Agent运行记录**、AGENTS.md/规范、实际运行的CI与工具/日志（可用什么读什么，不编造）。
- `docs/output/项目总控/项目实施状态.md`及模块依赖图。

## 按顺序执行

1. **事实验收**：核对本轮技术代码/测试/原版Review证据与业务验收；失败、未测或受阻的关键场景不能标为已签收；发现缺陷先回Bug处理和人工复测。
2. **调用Matt官方 `retro`**：在本轮收口阶段以**本轮AI编码会话**为复盘范围，明确调用 `skills/retro/SKILL.md`。官方 `retro` 会先调用 `writing-for-agents`，读取当前会话主来源，查找文件导航、自动化守卫、代码规范、AGENTS、工具经济性、无效指令与信息访问等真实改进机会，按严重度向用户呈现。此处不是重新开一个业务PRD评审，也不能改写为泛泛项目总结。
3. **沉淀可执行建议**：在 `docs/output/06-模块迭代/本轮retro改进建议.md` 记录症状、会话/测试证据、最小改进动作、负责人/审核、何时生效及下一轮验证方式；没发现有效问题则明确“本轮无可验证改进”。先征求用户或技术负责人的批准，**未获批准不得自动修改标准Skill、AGENTS、CI或已有全局基线**。
4. **更新项目实施状态**：只对实际签收模块改已验收；保留未完成和风险状态，并根据依赖关系确定下轮可选模块。签收结论不因retro发现改进建议而自动失败，但严重质量风险需记录并返回审核。
5. **进入下一轮/总验收**：存在未完成模块时，先带着批准的改进及注意事项返回“选择本轮模块”；全部签收则进入“全项目验收与部署上线”。**不用最后再独立执行一次相同的retro**。

> 官方retro的 `disable-model-invocation: true` 表示需要明确发起调用。本步骤的用户提示词会显式要求运行它；不应在无授权的普通编码对话中静默启动。

## 产物

## 门禁

- 有真实实现/Review/TDD证据和人工关键场景签收才能关模块。
- retro建议要有真实会话依据；**改进提议≠已经修改环境或代码**。
- 已批准的规范/CI/Skill改进可在下一轮生效，必须有验证机制。
- 无剩余模块才进入全项目验收，仍待完成则继续下一轮。
