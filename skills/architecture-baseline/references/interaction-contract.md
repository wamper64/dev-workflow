# 跨组件交互与场景追踪标准

## 1. 每条跨组件交互需要什么

| 业务触发/角色 | 发起组件→接收组件 | 接口与协议 | 身份/凭证 | 输入/输出及关联ID | 同步/异步及进度 | 超时/重试/失败/取消 | 谁持久化状态 |
|---|---|---|---|---|---|---|

协议和端点必须来源于真实对接资料，未知则标候选并在内部Grill裁决，不能自己把iframe服务写成gRPC服务。设计整体边界，不强迫所有接口在总体阶段精确到每个JSON字段。

## 2. 必须有的交互类型（按实际业务适用）

**本清单不是完整业务链路替代品**：每个跨组件交互必须能对应某条实际关键链路的具体处理步骤，或明确标注为认证/监控/备份等基础运行接口。关键链路应同时登记“触发、入口、判断、持久化、后续动作、完成与失败恢复”，详见 `core-business-flows.md`。

- [ ] Web页面→业务API（鉴权及用户上下文）
- [ ] 创建报价项目与上传文件（文件持久位置与版本）
- [ ] 触发需求解析/异步工作→进度/状态查询→结果（接受≠完成）
- [ ] 编排服务→Worker执行、结果、失败及取消，协议/超时/重试/回调机制
- [ ] iframe嵌入→短期访问凭证兑换→实际业务服务调用与数据隔离
- [ ] HITL暂停→人工确认/驳回→恢复/回退→记录身份与历史
- [ ] 知识库查询与数据同步（有则记录权限和知识来源）
- [ ] 多级审批与报价状态（不混同于AI编排）
- [ ] 文档生成/下载/归档与外部系统接口
- [ ] 跨组件日志/trace或correlation ID以便排障

## 3. 建议的图（按项目复杂度选择而非套模板）

1. **系统全景图**：所有已确认主要组件与交互方向，区分自有/第三方，必要时分组展示业务单元。
2. **核心业务处理流程+典型时序**：先画完整处理阶段及条件分支的流程图，再针对关键跨组件通信画时序图；包含状态Owner、失败与恢复路径。长流程可拆为主链加异常子流程，但必须从触发到最终业务状态闭合。
3. **人工确认/驳回恢复时序**：显示谁能继续、恢复哪一个执行实例以及审计。
4. **部署图**：组件与实际容器/主机关系及内部网络约束。

## 4. 下游合同

- 数据库总体从组件与交互取得权威数据Owner、事务/异步状态、审计与持久边界。
- 模块拆分取得组件职责和业务能力映射，不得在模块拆分时推翻既定部署单元。
- 模块详细设计在既定接口/状态Owner下补API字段、具体表/索引、异常和代码。

**与已有架构模板一致的表达**：全局拓扑只画一张平铺式组件图，在线上直接写协议/方向/传输内容；组件关系总表**不设置关系编号**，以发起方→接收方、协议、传输内容、成功和失败边界直接核对。独立的分层框图仅表达代码职责，不把类/模块画成独立运行服务。

## 全局通信语义与下游引用

- 受理不等于完成：HTTP 200、MQ ACK、第三方回执、AI返回不得直接代表权威业务终态。
- 写操作至少决定业务幂等键、重试停止条件、超时后如何查询/补偿/人工介入；设备控制等非幂等操作不能盲目重发。
- 身份、数据权限、traceId/requestId与业务主键/执行ID须能跨组件关联；缓存、iframe、Worker不应绕过权威服务。
- 可以给组件C01等稳定标识，但**关系不设置交互ID**，S05/S09以“发起方→接收方+协议/场景”引用。
