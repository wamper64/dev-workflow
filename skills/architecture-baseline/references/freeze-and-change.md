# 架构冻结与后续变更机制

## A/B/C规则

| 等级 | 冻结范围 | 变更责任 | 模块开发能做什么 |
|---|---|---|---|
| A 系统架构 | 组件/部署单元、工程组织、已批准基础设施、跨组件协议、业务状态和数据Owner、统一认证及网络安全边界 | 技术总监先批准S04变更，必要时ADR及同步下游 | 在既有组件与接口内扩展，不得偷偷新增服务/协议或第二数据Owner |
| B 全局规则 | 原型样式和通用组件复用、允许的代码依赖、统一异常/日志/追踪和授权规则 | 相关负责人评审兼容性例外，涉及A级升级至S04 | 按公共扩展点增加功能，不绕开规则 |
| C 模块细节 | 具体表/字段/索引、接口参数/DTO、业务局部算法、页面内部实现 | S09模块设计与S12实现审核 | 不突破A/B前提下细化 |

每项冻结条款要有“组件/代码对象、确认结论、禁止行为、允许扩展、检查方法”，不得写口号或把猜测冻结。高影响问题未确认时S04只能标候选待审核。

## 发现冲突的处理

业务模块发现须改变A项 → 暂停受影响的设计/实现 → 说明原方案、原因、候选选型、数据/代码/部署/安全影响及回退 → 技术总监审批 → 先更新S04（必要时ADR）→ 按影响修订S05数据库总体/S06环境/S07模块池/S09模块详细设计与相关测试 → 再开发。B项只是兼容例外且未影响A级时可由指定负责人审核；C项正常细化不重新开全局评审。

## 审核职责

项目经理核实角色×核心场景覆盖；开发人员用真实代码检验落点、复用和依赖；技术总监审批结构、协议、数据Owner、容量资源与A级冻结项。没有实际审核不得声称已通过。
