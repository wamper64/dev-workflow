> 本文件给出**可核对的通过条件**，不是"检查问题清单"。判定"通过"必须能指出对应的产出物；指不出即未通过。

## 2. 两轮审核的可执行等价物

**第一轮·双核心完整性关卡**：逐条核对上表"核心一 / 核心二 / 双核心双向"各行，产出物齐备即过。

**第二轮·链路可实施关卡**：**抽至少一条真实核心链路，逐步写出下列映射；任一步写不出即不通过**：

```
触发 → 接入 → 判断/处理 → 状态写入 → 后续动作 → 完成/失败
```

每一步都要给出：主责组件名、真实代码落点（文件/目录）、跨组件协议、数据/状态 Owner、部署位置、失败与恢复方式。

这一演练是 agent 可自行执行并留证的等价物，无需等待真人即可完成。

## 3. 角色会签（agent 不能代替，只能出核对结论并标"待会签"）

下列结论依赖真人判断，agent 只能**给出核对结论并显式标注"待会签"**，不得记为"已通过"：

| 角色 | 会签内容 | agent 的等价动作 |
|---|---|---|
| 项目经理 | 业务覆盖是否符合预期；范围取舍（如不做某类通知）是否可接受 | 按角色×场景过程性核对覆盖，输出覆盖结论与范围外清单（不另出表），标"待会签" |
| 技术总监 | 组件/协议/数据Owner/A 级冻结/资源闭合 | 输出 A/B/C 冻结清单与资源闭合表，标"待会签" |
| 开发人员 | 代码落点、复用与依赖、链路可实施 | 执行上文第二轮演练并留证 |

未会签前，正文第五章相应条目只能标"待会签"；未实际发生的评审不得记为"已通过"。审核不另出文件。

## 4. 失败的典型与成功的定义

**失败的典型**：只画 `第三方→后台→MQ→数据库` 而缺判断/去重/落库/通知/确认；只画 `前端→后端→DB` 而无处理链；把逻辑模块拆成微服务；无证据强加 MQ/OSS/独立服务；同一业务状态有两个写入者；把基线台账重抄一遍；用编号代替名称；把示例组件当作本项目事实照抄。

**成功的定义**：完成两个不可替代的交付——**全项目总体组件架构**与**每类关键业务的端到端处理链路**；经双向校验（链路步骤→组件→交互/Owner/代码 与 主要组件→需求场景/处理职责）闭合；第一轮审查覆盖与完整性，第二轮由开发者依真实链路演练代码落点与异常恢复；角色会签留待真人。
