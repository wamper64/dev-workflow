# 整体架构骨架的审核门禁

| 关卡 | 检查问题 | 不通过处理 |
|---|---|---|
| 全部输入 | 是否遍历 docs/input/ 所有类别/文件，确认PRD/工程/环境/对接实际事实并记录缺失？ | 未读到的关键资料先补读，不能只看PRD |
| 硬约束 | 项目基线技术版本、8C16G等实际资源、并发、P95/存储留存是否与组件设计一致？ | 先Grill或申请基线变更 |
| 组件覆盖 | 每个业务能力/第三方/Agent/Worker/审批/知识库是否有组件归属？ | 补组件及依据 |
| 完整骨架 | 组件逻辑图、实际进程或外部系统划分、部署拓扑能一一关联？ | 区分逻辑和物理边界 |
| 相互交互 | 每条主要边记录协议、调用者、身份、请求/响应、状态、超时、失败和回退？ | 补交互矩阵及时序 |
| Worker类型 | 若存在原生Worker、iframe/REST集成，不得用单一“Worker服务”统称，更不得把iframe写成gRPC。 | 回读对接资料，细化边界 |
| HITL与审批 | 编排暂停人工确认与业务多级审批是否区分，操作者如何授权、驳回后怎么回退？ | 补状态/鉴权/时序 |
| 数据所有权 | 业务状态、长任务执行状态、文件与知识检索状态谁是权威，能供数据库总体设计使用？ | 补Owner |
| 资源部署 | 所有确定部署单元均有服务器/容器归属、资源配额、网络与恢复边界且总量能闭合？ | 调整架构或修改已批准的预算 |
| 工程复用与依赖 | 实际扫描code/路由、UI、权限与后端模块，已给出新增位置、公共能力复用及允许/禁止依赖吗？ | 补实际工程映射；不得重建原型或重复造轮子 |
| 项目专项 | Web/IoT/Agent/第三方是否按真实触发证据判定启用、叠加或不适用？ | 补证据及对应组件、接口/状态/部署；删除无依据服务 |
| 架构冻结 | 已定A/B/C决策是否有禁止/允许扩展与变更路线？还有没有高影响未裁定问题？ | 补具体冻结契约；高影响阻塞不得放行 |
| 下游可填充 | 随机抽一条真实场景，开发人员能定位前后端代码、复用接口、组件依赖、状态Owner与部署吗？ | 技术总监退回整体设计 |
| 来源诚实 | 示例/候选/已裁定有区分，不能声称读取了仓库中实际未提供的PRD、Worker接口文档。 | 删除臆造事实并内部Grill |
| 审核结论 | 项目经理确认业务覆盖、技术总监确认系统结构和交互，且审核证据真实。 | 不得宣布完整已审核 |

**失败的典型例子**：只画 `Vue→若依→MySQL→Redis`，却没有体现实际报价系统各Worker及编排链；只列组件没有接口和状态；单机拓扑中添加未核准的新服务；未区分程序逻辑模块与独立部署单元。

**成功的定义**：第一轮核对“角色×核心场景→组件/交互/Owner/部署”无遗漏，第二轮由开发人员抽真实场景核对“代码放哪→复用什么→可依赖谁→异常由谁处理→哪些已冻结”，均有证据。项目经理确认业务覆盖、开发人员确认工程落地、技术总监确认组件协议与A级冻结；未实际审核不得填通过。

- [ ] 与既有模板一致：第一章背景/边界/指标/环境/选型/外部对接；第二章平铺拓扑/分层图/完整组件清单与无编号关系表/关键链路/权威数据；第三章容量及运行参数；第四章部署安全运维恢复；第五章A/B/C冻结、风险与未决问题。
- [ ] 前期已经在需求基线或工程基线确认的数值继承，不在整体架构重新讨论；模板示例组件全部依实际项目替换。
