# 组件全覆盖与三层分离

本清单用于发现漏掉的真实组件。不是一个强制微服务列表，只有输入事实或架构决策证明需要的组件才写成“确定”。

## 1. 三种层次不能混为一谈

| 层次 | 必须回答什么 | 举例 |
|---|---|---|
| 业务能力/逻辑组件 | 功能职责是什么，哪些状态归它裁决 | 报价审批业务能力、参数版本管理 |
| 系统交互接口 | 谁以什么协议调用谁，带什么身份或执行标识 | Web→REST；原生Worker→gRPC；iframe接入→业务REST（仅当资料确认） |
| 运行部署单元 | 一个组件和多个组件是在同一进程还是分别运行？装到哪台机器 | 现有若依进程内的业务模块，或独立Worker容器 |

## 2. 必扫组件类别

- [ ] 终端和业务界面：现有Vue/React原型、主系统导航、iframe外部页面、AI前端运行时（有则列明）
- [ ] 服务接入和安全：Nginx/API入口、若依登录授权、数据权限、跨Worker身份/凭证转换
- [ ] 主业务：项目、需求资料及参数确认、匹配、成本、报价版本、审批/HITL、客户文档/归档、审计报表
- [ ] 智能化/编排：Agent/统一编排、Workflow执行状态、可恢复等待、人机确认、异步执行调度
- [ ] 执行单元：每个已确定的独立Worker或外部模块、能力、输入/输出、gRPC/iframe/REST的真实接入类型
- [ ] 知识库：RAG/文档导入、检索服务及其知识索引所有权（如PRD实际需要）
- [ ] 数据：事务数据库、缓存/临时状态、对象/文件存储、审计、备份恢复；是否独立存储须由事实判断
- [ ] 外部依赖：报价计算工具、第三方数据库/ERP、设备与接口、认证系统、正式环境权限
- [ ] 运维：部署入口、日志与健康、告警、定时任务、备份与恢复

## 3. 逐个组件最少字段

| ID | 名称 | 逻辑/外部/存储类型 | 业务责任 | 自建/既有/第三方 | 输入依据 | 主要交互方和接口 | 状态/数据Owner | 部署单元 | 确认状态 |
|---|---|---|---|---|---|---|---|---|---|

要求：每项都与 `docs/input/` 某份资料或已确认Grill结论形成可追溯关联；同一组件不能因出现在不同流程而被重复造一个实例。

## 4. 遗漏与误划分的否决测试

1. 任选一个PRD核心场景，找不到承载组件或者跨系统接口 → **遗漏**。
2. 某个Worker已在对接资料中存在，但组件清单里只有“外部服务”泛称 → **遗漏具体责任**。
3. 一个用户动作横跨两套未定权限域，图中没有身份传递 → **交互不完整**。
4. 将现有若依的用户、角色、数据权限再做一个独立权限系统且无理由 → **重复建设**。
5. 组件图包含某服务，但部署拓扑和接口表都没有它 → **骨架不能落地**。
6. 只画Nginx/前端/API/DB，不展示真实业务编排与六个Worker等对接能力 → **项目适配失败**（仅当输入资料确有这些能力）。
