# 整体架构设计：总体组件架构 × 核心业务链路

## 1. 唯一目标和完成判定

本 Skill 不是“列几个运行服务”或画一张 Web→API→数据库图，也不是只有接口连线却没有处理过程。它围绕**两个同等重要且相互校验的核心**建立开发前系统架构：

- **核心一·总体组件架构（系统由什么构成）**：识别全项目真正需要的逻辑组件、前后端工程模块、运行单元与外部系统；明确每个组件职责/非职责、代码落点、复用、依赖、跨组件协议、数据与状态权威，以及部署关系。
- **核心二·关键端到端业务链路（业务如何在这些组件中跑通）**：从业务触发条件出发，完整确定**进入→接收/校验→必要的异步缓冲/转换→业务判断/处理→持久化及结果确认→通知/外部动作→反馈/处理/闭环**等**按实际适用**的步骤，逐步写出由谁执行、输入输出和状态、同步/异步交接、成功/失败以及恢复方式。不是所有业务都需要队列、OSS或通知，需根据真实需求和约束裁定。

**双向闭环**：从关键链路反推缺失的组件，再从组件总表校验每个处理步骤的Owner、接口和部署；**每条关键链路必须能在架构图与组件与关系总表追溯，每个承担业务处理的主要组件都要能对应需求链路或明确的基础运行职责**。形成后续数据库总体设计、模块划分和逐模块详细设计必须遵守的系统骨架。

“所有组件”包括按真实需求需要的前端业务界面、后端业务能力、Agent/编排服务、Worker/执行单元、工作流与人工任务、RAG/知识检索、数据库、缓存、文件存储、网关/权限、第三方/设备接入、监控备份等；按资料判断其**必需、可复用、可选或不适用**，不得固定某个技术产品、不得漏掉PRD和对接资料中出现的角色。**组件不是容器**：同一组件可以是同进程逻辑模块，也可能是一个独立进程；必须分别说明逻辑边界与部署单元。

完成后，开发人员应能在不重新发明顶层组件的前提下，直接从骨架中选出某一模块，继续细化页面、API、数据表和内部实现。

**S04冻结的不仅是组件及其接口，也包括关键链路的处理顺序、状态边界、交接语义和异常恢复原则**。不得因为后续模块实现方便，就私自改变数据接入后的处理链、取消去重/授权/持久化或将已确认的同步流程改成异步流程。

**S04是开发前的系统架构冻结关卡**：必须决定新代码放哪里、复用什么、允许依赖谁、谁裁决数据和业务状态、哪些结论不得由模块自行更改。必须覆盖十个维度：系统边界、技术与复用、前后端工程结构、组件职责、交互、数据Owner、安全、容量可靠性、部署运维、冻结和演进。IoT、Agent、第三方等专项只按真实触发条件启用，参见 [专项适用性](references/architecture-applicability.md)。

## 2. 输入——必须全面读取，不得凭想象

1. 遍历 **`docs/input/` 下全部现有目录和文件**，不只读取PRD：需求资料（项目/模块PRD与补充说明）、工程资料（工程方案/已有技术选型）、环境资料（服务器/网络/硬件）、对接资料（真实第三方、Worker/设备接口、协议、认证等），以及以后新增的类别。PDF/Office/Markdown等可读文件按实际可用方式理解；内容相互矛盾应指出。
2. 读取 `docs/output/01-项目基线/项目基线.md` 中**已确认**技术栈、CPU/内存/磁盘、并发/性能、数据保存、权限/部署/恢复硬边界；已有输入核对结果只作线索，不替代原始资料。**正式交付文档必须自足**：本决策依赖的具体值（版本、容量、留存、规格、时限、上限）就地写出数值并标注权威来源，不得用"见某文档"代替；引用上游只针对推导过程、完整清册与假设集。
3. 检查 `code/` 中实际工程的构建配置、代码模块/包、路由/页面/布局/组件、前端API封装、后端公共权限/字典/文件/日志及业务扩展点。输出实际“已有能力→复用/扩展→新代码落点→禁止重复建设”的映射，供组件表「归属·依据」列使用；不得把模板示例中的子目录视为已扫描事实。
4. 读取已有 `GLOSSARY.md`、`docs/adr/`、方案决策和已经形成的系统接口文档（存在才读），确定继承约束，不重复质疑已确认业务决策。
5. 对缺失、不可读或互相矛盾的资料先说明“影响什么组件/交互”，不能以猜测补成已确认架构。读取 `references/component-inventory.md` 和 `references/interaction-contract.md` 的全覆盖检查项。

## 3. 执行方法（Grill 在本 Skill 内部）

### 3.1 先识别关键业务链路，再反推需要的组件

先阅读 [核心业务链路标准](references/core-business-flows.md)：对所有PRD角色×核心场景及真实对接业务进行**关键链路筛选**，至少覆盖本项目实际存在的主业务闭环、数据/事件进入及处理、重要外部交接、审批/人工确认或异步长任务、设备命令与回执、关键通知/归档等不同类型。普通CRUD和仅展示页面可按同类合并，**不要求每个功能点画一张流程图**。

每条选中链路先做**端到端处理步骤草图**，标注触发方、入口、先后次序、条件判断、业务状态迁移、权威数据落点、消息/文件/通知交接及成功/失败/恢复出口。再从“哪个步骤需要哪个实际组件/公共能力”反推总体组件候选，核对现有code/与外部合同能否承载。**不要先决定必然有MQ、OSS或独立告警服务，也不能画完组件图就跳过流程设计。**

流程草图和组件总表需要迭代校验：发现步骤没有Owner就补齐组件或已有模块职责；发现新增组件没有场景/运行依据则合并或删去；发现流程要求与基线技术/资源不兼容则内部Grill确认取舍。

### 3.1.1 从业务链反推组件，而不是先选技术

梳理PRD中的**业务场景 × 系统能力 × 外部对接方**，提取组件候选：用户操作、核心业务对象与状态、数据解析/规则计算、人工核对、审批、文件导出、知识库、外部执行单元/第三方、运维等。每项都标记来自哪个原始资料以及是否已有可复用实现。

区分三层：**业务能力/逻辑组件**（做什么）、**交互接口**（谁调用谁）、**运行部署单元**（实际上以何进程/服务运行）。不能按业务步骤数量机械新建微服务，也不能遗漏由真实工程资料确认的独立运行单元。

### 3.1.2 适用性判定：固定十维度，按条件启用专项

从PRD/对接资料/真实代码形成“项目类型→触发证据→启用/不适用/待裁决→对应组件Owner”表。普通Web/审批、工业IoT设备、Agent与知识库、第三方系统集成允许叠加；**是否引入队列、OSS、独立服务等一律按触发证据判定（通用规则以 `references/core-business-flows.md` §4 为唯一权威），不因为业务涉及 IoT/AI 就默认引入**。启用专项必须在组件、交互、权限、状态和部署图体现；**未启用的专项不写**（其"不做"已在系统边界表达），不生成"不适用"清单。详见 [专项条件清单](references/architecture-applicability.md)。

### 3.2 调用官方 Grill 作内部决策子流程

当下述关键点在输入中仍未裁决时，**直接调用 `grill-with-docs`**（`skills/grill-with-docs/SKILL.md`），它依次使用 Matt 官方 `grilling` 与 `domain-modeling`：

- 谁负责整体编排、业务状态/审批状态和长任务持久状态；是否采用独立编排服务；传统 Java 工作流与业务审批引擎的边界；
- 当项目确有Agent/Worker/第三方执行单元时：哪些独立部署、哪些嵌入或通过REST/消息/gRPC等契约交互，异步执行、超时、回调与HITL（如适用）如何衔接；
- 与现有后端业务系统的身份、项目权限、会话传递方式；外部 iframe、第三方服务及知识检索鉴权和租户边界；
- 数据/附件/知识索引权威来源、失败重试、超时回滚、部署与资源预算取舍。
- 既有工程中应复用还是新建公共能力、真实代码目录及依赖方向、逻辑模块是否有独立运行单元的必要性。

按**依赖决策树**逐轮只问用户必须裁定的问题，每项提供基于已调查事实的建议和备选。Grill 中发现术语冲突及时澄清；只有满足“难逆转、非显然、真实取舍”的决策才创建 ADR。**已经在项目基线/PRD/对接资料确认的决策不要重问**。如没有未决架构分歧，直接跳过询问并继续，仍要校验组件总表是否完整。

未回答且会改变主干拓扑的问题不得直接猜测并宣布完成；可输出候选方案供审核。

### 3.3 建立完整组件骨架

按 `references/component-inventory.md` 形成**全局平铺拓扑 + 组件与关系总表**（一张表、组件为主键、对外交互内联、不设关系编号）。每个主要组件必须写出：组件名、类型与运行形态、职责与非职责、归属主体（自建/既有/第三方）与代码或资料依据、对外交互（对方·协议·方向·同步异步）、关键数据/状态 Owner、部署方式（同进程/独立/外部/待裁定）。**工程复用与代码落点就写进组件表「归属·依据」列**：原型视觉/布局/公共组件保留，已有登录/字典/文件等能力优先复用、不得建第二套；业务模块不得绕过公开接口直写他模块内部 Mapper/表，禁止无依据引入独立微服务。

明确真实系统内外边界：已有Web/后端、存储、中间件及实际第三方；若项目存在Agent/编排、Worker、知识库或审批/HITL，再根据输入列入图中。一个业务阶段若涉及多个组件，按实际关系画；若组件尚未获确认，绘为**待裁决**而不是成品既定架构。

**跨边界分类**：每条跨边界连线要判断"是否经过本系统"，分为两类——业务接口（必经本系统，含鉴权与租户边界）与浏览器资源/媒体加载（浏览器直连第三方，如地图 SDK、视频 SDK/流）；后者必须在图中注明。既有 `code/` 与对接资料是**复用参考**（表征已有能力与外部合同），不是设计结论的“证据”：本文写决定与理由，不逐条挂 `文件:行` 引用。

**运行单元可内展开**：一个进程/容器内有多个核心逻辑组件时，在同一节点内用子图/子列展开（不新增网络节点），让"进程里有谁"可读；拆成独立网络节点仅当有独立部署、隔离或容量证据。**组件、链路、问题一律用语义名称，不造 C01/L1 之类编号**（仅当对象被反复跨节引用且名称过长时才允许编号，且须与名称同现）。

### 3.4 深化第二核心：完整的关键业务处理链与组件协作时序

在组件架构初稿完成后，按照 [核心业务链路标准](references/core-business-flows.md) 将每条关键链路草图深化为**可直接指导后续设计的架构级处理流程图**，并为跨组件关键路径补充**时序图**。

每条链路的必备要素：**起点与触发条件、先后顺序/判断分支、每步负责的组件名/逻辑模块、输入输出与关键事件、传输/交接方式、数据/状态权威与持久化时机、同步/异步/通知、结束状态，以及重复/超时/失败/恢复闭环**。应决定处理职责与可靠性策略，不提前展开算法公式、规则配置字段、具体DTO/DDL/Controller。**流程图的节点写"谁做什么"，不写编号；同一业务状态只能有一个权威写入者。**

**例如设备告警链路**（仅示意，需以实际项目资料判断是否使用队列）：
设备/第三方上报 → 接入组件鉴权与解析、数据质量校验 → 【必要时消息队列缓冲与消费者】 → 业务组件做阈值/状态/去重等告警条件判断 → 权威告警状态落库/确保重复事件不多次创建 → 根据已持久化告警事件触发通知 → 通知服务发送、失败重试或人工兜底 → 授权用户确认/关闭并保存结果。须明确“上报成功≠产生告警”“写库成功≠通知成功”，并识别晚到、乱序、设备离线、第三方故障的出口。若场景没有通知/确认或消息队列，则按证据删除该步，不强制套模板。

**关键链路不应只画成“第三方→后台→MQ→数据库”**：其中必须出现告警判断、写入权威、通知和业务闭环等架构级处理动作；链路步骤映射到组件与关系总表，该表的关键交互必须能在相关链路或基础架构中找到依据。

### 3.4.1 画全部主要交互，不止一个箭头

按 `references/interaction-contract.md` 产出**组件与关系总表（关系内联、不设关系编号；即 2.2 同一张表）+ 核心交互图（Mermaid flowchart/sequenceDiagram）**（组件与链路用语义名称，不用编号）：
- 发起者/接收者、触发场景、REST/gRPC/事件/iframe/API等**协议按真实对接资料确定**；
- 身份/凭证转换、请求或业务数据、同步响应、进度/回调、持久执行状态、失败/超时、幂等/重试、取消、人工确认与继续条件；
- 从实际业务触发源到可观察结果的端到端跨组件主链；存在文件上传、审批驳回、生成下载、Worker串/并行或HITL时，分别画适用分支与状态恢复。
- 必须覆盖PRD列出的所有**不同交互类型和边界**，不是为每个 CRUD 页面单独画时序图。

组件交互不能只写“API调用”；至少解释谁调用谁、用什么协议、谁持有执行状态、异常怎么返回或恢复。跨组件数据归属与访问权限不能与项目基线冲突。

### 3.4.2 核心链路 × 组件的双向一致性

使用“链路/步骤→执行组件→代码落点状态（已扫描存在/规划新建/外部合同）及其证据→对应组件交互→数据/状态Owner→异常与恢复责任”矩阵，核对**流程每一步有承载、主责组件每项主要能力有链路依据、同一业务状态没有两个权威、图/表处理顺序一致**。异步链路需明确消息受理、业务持久化和通知交付的分别成功标准；跨系统失败须有停机/补偿/人工处理出口。组件或交互发生架构级变化时必须同步修改链路图及冻结规则。

### 3.5 运行部署与资源适配

绘制**部署单元拓扑**（与逻辑组件图分开）。按环境资料与基线填写运行单元、主机/容器、内部端口与协议、CPU/内存/磁盘预算、持久卷、网络/出网、健康状态及备份恢复边界。无硬件授权/部署资料时写候选而非“已经部署”。不凭行业常用架构或案例假设Redis、MQ、Agent或额外运行单元已经部署。

### 3.5.1 架构冻结及后续开发变更规则

按 [架构冻结与变更契约](references/freeze-and-change.md) 将真实已批准的结论分为A：系统组件/独立运行单元/跨组件协议/数据权威/统一权限等必须技术总监批准才可改变；B：公共组件复用、代码依赖、异常、审计、原型保真等全局兼容规则；C：业务表字段、DTO、Controller、局部页面与算法等模块内部细节。每项写清“批准的决定→禁止行为→允许扩展→检查方式”。重大修改先评估S05/S06/S07/S09/S12影响，先评审更新S04，再改下游，不得由模块开发私改。**该变更流程属技能/流程约定，不在交付文档另立章节**；交付物只写 A/B/C 冻结清单本身。

### 3.6 交付骨架的可用性校验及技术总监审核

用 `references/architecture-gate.md` 的两轮审核：
- **第一轮·双核心完整性关卡（过程执行、不落盘）**：核对角色×核心场景→组件/代码覆盖，以及核心业务**关键链路→每条处理流程图→组件/交互/状态Owner→正常与异常终态**完整；覆盖性问题以结论形式并入第五章，不另出覆盖表。设备告警等事件处理不能只有“接入→数据库”省略必要的判定、通知和业务闭环。专项按真实触发启用，主要组件不得没有实际链路或基础设施依据。
- **第二轮·链路可实施关卡**：任选至少一条真实核心链路，让开发人员沿实际处理流程逐步指出**触发→接入→判断/处理→状态写入→后续动作→完成/失败**对应的已存在代码模块或计划新建落点（明确标记）、组件关系、依赖、数据Owner及运行位置；检查丢消息、重复、超时、外部不可用是否有原则上可实施的处理。S05/S07/S09在此基础上只需细化存储、API字段和业务算法。A/B/C冻结项可引用，影响主架构或关键链路处理策略的阻断项未裁决则不得放行。

项目经理确认业务场景覆盖；技术总监确认整体骨架、资源、协议和关键选型。组件边界变更应先评审更新本设计，再允许下游调整。**审核结论（未决、冲突、会签）并入正文第五章，不另出文件。**

## 模板约定

交付正文依照已提供的整体架构设计模板：**1 系统概述 → 2 总体架构设计 → 3 关键运行参数和值 → 4 部署、安全与运维 → 5 架构冻结、风险与剩余问题**。第二章按两个主核心组织：**2.1 总体组件架构视图**（全局架构拓扑）；**2.2 组件与关系总表**（一张表，组件为主键、对外交互内联、不设关系编号）；**2.3 关键业务链路**（逐条端到端处理流程图 + 必要跨组件时序图 + 步骤 Owner + 状态/异常和完成判定）。关键数据存储与结果判定放 **3.3**。**结构服务于阅读**：交付物是一篇连续的文章，不设"目录/清单"重复其后的正文、不把内容切成大量编号小节、不逐条挂文件行引用；未启用的专项不写。关系线上直接注明协议/方向/数据，不以编号代替业务信息。正式正文只写裁定值，工作过程和推荐留会话；未解决的高影响问题只放第五章。双向核验与角色×场景覆盖核对是过程，不产出独立表格，其影响设计的结论并入第五章。

**新建功能真实性规则（F09）**：链路步骤需有可实施的代码归属，而非要求首次开发的源码已存在。所有落点明确三态：`已存在`（扫描到真实路径并可定位）、`计划新建`（已批准目录/类/接口方案，不能声称文件已存在）、`外部合同`（实际对接资料）。未能定位现有文件时写“计划新建/待裁决”，不得造文件名当实测证据。
