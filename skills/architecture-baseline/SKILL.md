# 整体架构设计

## 必需输入与前提

读取`docs/output/01-项目基线/项目基线.md`，`docs/input/需求资料/`的确认PRD、`docs/input/工程资料/`、`docs/input/环境资料/`、`docs/input/对接资料/`、`code/fld/`及`code/guiwu_ruoyi/`的实际结构；复用前一步 `grill-with-docs` 裁定的关键架构决策和GLOSSARY/ADR。**项目基线中的版本、CPU/内存/磁盘预算、性能与数据保存要求是硬约束**，不能由架构设计擅自改写。

## 执行顺序

1. **确认运行单元**：识别原型Web、RuoYi业务API、已有认证模块、数据库、缓存、文件存储、第三方接口与可能需要的任务/AI执行单元。根据真实业务决定哪些必须独立进程、哪些保持RuoYi单体模块；不能为每个菜单创建微服务。
2. **确定服务责任**：各单元分别承担什么、不承担什么；谁拥有交易状态、用户身份、报价版本和审批一致性；避免同一数据同时被多个服务任意写入。
3. **定义交互与失败路径**：Web→REST、必要的后台任务受理/查询/取消、第三方超时重试、鉴权与权限下沉、通知/回调可信校验、文件访问、幂等及版本检查。明确同步与异步切换点。
4. **完整链路校验**：按确认PRD走一遍“登录→项目→需求解析及人工核对→计算单匹配→成本核定→报价→审批→归档”和对应的异常/驳回链，画每条跨单元调用的责任。
5. **部署和资源校验**：画实际部署拓扑，落实既有项目基线的CPU/内存/磁盘/网络和容量限制；不能画出预算无法支撑的新组件。校验备份、恢复、灰度或重启规则与基线不冲突。
6. **替代方案与审核**：只有高代价、跨模块不可逆的方案变更才比较两种以上选择并引用必要ADR。调用 [总体架构评审清单](references/architecture-gate.md) 校验后提交技术总监，不通过则修正架构，基线不适配时先申请变更，禁止偷偷放宽基线。

## 输出

按 [总体架构交付模板](assets/architecture-template.md) 生成：
- `docs/output/02-整体架构/整体架构设计.md`
- `docs/output/02-整体架构/架构评审记录.md`
- 符合ADR触发条件时更新 `docs/adr/` 现有编号体系。

**边界**：只设计运行架构、跨边界一致性、全局鉴权、部署与容灾。不设计每个页面实现、Controller、DTO字段、每张业务表字段；这些交给当前迭代模块详细设计。前端继续使用`code/fld/`，后端继续扩展`code/guiwu_ruoyi/`。
