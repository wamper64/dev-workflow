## 2.3 核心二：关键端到端业务链路

**本节与组件架构同为S04核心交付。** 不能只画“第三方→后端→MQ→数据库”。要画清业务处理过程，比如设备数据的校验、条件判断、告警去重与持久化、通知与确认及异常恢复。每个环节必须有执行Owner。队列、OSS、通知、独立服务按实际需要决定，绝不因为模板出现就默认选用。

从已确认PRD、原型业务动作、工程/对接资料中选取真正影响架构的链路：**主业务闭环、数据/事件进入后处理、跨系统交接、重要审批/人工确认/长任务、设备控制与回执（实际存在时）**。普通同构CRUD可合并。链路数量不固定，也不按菜单或业务模块逐一画图。

### 2.3.2 每条链路必须交付什么

每条链路都要提供：

1. **业务处理流程图**：从触发到最终结果，必须出现处理动作、条件分支、主要组件Owner、至少一个重大失败/恢复出口。只有组件名之间的连线不合格。
2. **处理步骤与责任表**：明确每一步的组件/现有代码落点、业务输入输出/事件、协议、同步/异步、权威数据/状态写入时机和成功标准。
3. **跨组件时序图**：当确有复杂跨服务交接、消息、回调、人工等待时补充；主要展示调用先后、ACK/回执、结果归属，不能用它取代业务判断流程图。
4. **状态与异常闭环**：区分“已受理、业务处理成功、权威状态持久化、通知/外部动作交付、人工处理完成”；覆盖重试、幂等、迟到、超时、失败、回退与人工兜底。
5. **粒度边界**：本阶段定处理链/条件类别/权威/可靠性原则，不提前设计全部告警阈值参数、DTO字段、业务DDL或具体Java方法。

**设备告警链路示例（仅说明深度，不代表项目默认采用）**：

设备/第三方上报 → 接入组件解析、鉴权、校验数据质量与采样时间 → 【流量或解耦需要时采用队列缓冲】 → 告警规则组件判定条件 → 无告警则更新正常监测状态；触发告警则幂等创建/更新权威告警记录 → 【需要通知时】可靠交接告警事件/通知任务 → 通知服务发送与记录成功/失败 → 【存在告警处理业务时】授权人员确认/关闭。

必须区分：**接收上报成功≠产生告警；告警落库成功≠通知成功；通知成功≠人员已处理**。需要明确重复、乱序、离线、MQ/通知失败时谁负责恢复。没有队列、通知、人工确认需求时应删掉步骤，而不是额外创造需求。
