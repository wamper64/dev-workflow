# 本轮模块详细设计

## 目标

形成真实可开发、可测试、可审查的模块设计，而不是摘要或空模板。输入是 `docs/output/06-模块迭代/本轮模块计划.md`、本模块PRD、已有 `code/fld/` 原型页面与 `code/guiwu_ruoyi/` 扩展点、项目基线、整体架构和数据库总体设计。若前置 `grill-with-docs` 存在已确认决策/ADR，必须继承，不重开PRD的已定问题。

## 实现流程

1. **画模块边界**：锁定本轮模块负责的核心业务对象、用户角色、页面入口、上游数据和下游消费者，拒绝扩大到未排入本轮的模块。
2. **设计业务规则与状态**：按模块PRD建立成功、失败、重试、取消、驳回/重提等真实状态迁移；写清权限、谁触发、幂等、并发冲突、版本可追溯。关键对象应有状态表或状态图，不用大段叙述掩盖分支。
3. **对齐已有页面**：给出页面→业务动作→接口→后端服务映射；先定位原型现有组件/样式与若依公共能力，只做接入和必要局部更改，禁止另建同功能页面。
4. **设计数据结构**：严格在已审定的数据库域中，针对本模块给出具体业务表、字段名/类型、唯一性、索引、外键逻辑、幂等键、租户或项目权限过滤、历史版本与归档规则；准备迁移设计草案（非可执行SQL）；待TDD编码阶段生成版本化脚本，若实际脚本与草案不符，须反向修订详细设计并重审。
5. **设计API契约**：每个业务动作列 HTTP方法/路径、角色/权限、参数结构、成功响应、业务错误码、事务边界、分页过滤与重复请求处理；跨模块接口应有生产者/消费者和兼容性说明。
6. **风险与质量验证**：将已确定的工程基线（例如CPU/内存、并发、保留年限、P95）逐条落实到设计约束；选择最高可用的测试接缝，优先复用已有接口/服务边界，交 `to-spec`。
7. **设计审查**：调用 [模块设计门禁](references/module-design-gate.md)。设计涉及总体权限、数据域或系统部署改变时停止并提请技术总监重新评审，不得在模块设计中私自改变整体基线。
