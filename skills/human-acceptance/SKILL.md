# 人工测试用例生成与结果回填

## 定位

**这不是再次让AI做一次自动测试，也不是让AI签收业务。** 前一步 Matt `implement-spec` 已负责TDD、必要集成验证和内置代码评审。本Skill只负责生成**真正需要人做的测试单**，并在测试执行后根据人工提供的实际证据更新同一文档。

## 输入

- `docs/input/需求资料/` 下**已确认的需求基线**：项目PRD、模块PRD、原型及角色×核心业务场景。
- 本轮已选模块Spec、Tickets、详细设计，必要时参考工程基线与全局组件交互骨架。
- `code/fld/` 的当前页面及已有原型；若依真实业务实现。
- `implement-spec` 已执行的TDD/集成验证、内部code-review结论和未覆盖事项。
- 真实测试环境、账号角色、第三方是否可用（账号凭据不可写进测试单）。

## 两个连续的动作

### 动作一：由AI编制人工测试单

1. 将需求基线里的**角色×核心场景**与前一步已经真实运行的测试结果对照，去掉只是机械重复单元/API测试的用例。
2. 选择AI无法可靠证明的事项：实际UI视觉与原型差异、交互体验、复杂操作、人工业务判断、审批流多用户行为、真实第三方与文件交付效果。
3. 为每项写清`用例ID / 角色与场景 / 前置数据 / 操作步骤 / 预期的可观察结果 / 实际结果 / 测试人 / 执行时间 / 证据 / Bug`。
4. **状态一律“待执行”**，实际结果与截图列为空。AI不得擅自写“通过”。

### 动作二：开发人员执行并回填

1. 开发人员打开页面、按用例操作，亲自填写`通过/失败/受阻/不适用`和实际结果、时间、环境、截图/业务结果证据。
2. 发现缺陷：在同一表中记录Bug编号和复现说明，调用 **Matt官方 `diagnosing-bugs` 原版六阶段**。修复后由人按原测试用例复测，并在该用例的复测列写真实结果。
3. 若第三方不可用，只能写“受阻”或“模拟验证通过、真实业务未验收”，不能写通过。
4. 项目经理按角色×场景核对真正通过/受阻/未执行的情况，未通过不能进入迭代收口。

## 唯一正式输出

- `docs/output/06-模块迭代/<模块>/人工测试用例与结果.md` —— **一份文件分两个时间点完成**，不再强制创建一套重叠的报告。
- 如有缺陷可附 `缺陷记录.md`，但人工用例与复测结果仍以主文件为准。
