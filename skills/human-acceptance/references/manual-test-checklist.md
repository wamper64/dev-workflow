# 人工测试与签收检查标准

## 只有人能够签收的内容

- 原型页面整体观感与原有风格是否一致，是否未经批准改版。
- 复杂表单的焦点、回车、错误提示、弹窗层级、分页、加载和退回是否符合实际操作预期。
- 真实角色的业务权限，以及各级审批后的状态与待办变化。
- 业务计算/导出文件的真实可用性、内容准确性和客户确认方式。
- 无法由AI调用的第三方、现场设备、正式客户账号或人工审批。
- 极端数据/异常和多用户同时操作中的可理解反馈。

## 单个用例结构

| 字段 | 必填内容 |
|---|---|
| 用例ID | 唯一且可回溯模块/场景 |
| 角色与场景 | PRD对应角色、核心业务场景 |
| 前置条件 | 账号权限、数据版本、环境和依赖 |
| 操作步骤 | 可由另一位开发者照做 |
| 预期结果 | 实际可观察的页面、数据库或业务状态 |
| 实际结果 | 人工填写，不可由AI预写为通过 |
| 状态 | 待执行/通过/失败/受阻/不适用 |
| 证据 | 截图、视频、日志、对应记录ID（脱敏） |
| 缺陷 | Bug编号、严重性、关联Ticket |
| 复测 | 修复版本、执行人、复测证据 |

允许“模拟通过”，但不许将其等同正式第三方联调。发现BUG要定位最小反馈环，不得盲修。
