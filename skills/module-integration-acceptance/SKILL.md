# 模块联调与 AI 可验证测试

## 1. 触发与边界

当前模块的 Tickets 已按 TDD 实现并经 `code-review` 评审。使用已部署的本地环境，在真正的 `code/fld/` 与 `code/guiwu_ruoyi/` 工程里完成端到端联调，不重做 UI，也不替代人工业务验收。

输入：当前迭代 Spec、Tickets、模块详细设计、数据库迁移、当前原型页面、真实运行的开发环境、已批准的依赖和第三方接口资料。

## 2. 先检测可自动化的测试面

读取 [验证矩阵](references/verification-matrix.md)，优先复用项目现有测试设施。Java 8/RuoYi 检查原有 Maven/JUnit 集成方式，Vue/Vite 检查现有前端测试和浏览器测试框架；不要未经确认另引入全套测试基础设施。

从 Spec 的角色×场景要求中划分三个结果：
- 可自动执行的接口、数据库、权限、异常和 E2E：实测并保留命令/证据。
- 可浏览器验证的原型一致性：检查是否在现有路由和组件上改造、相同页面主结构是否保持、设计语言是否继承；有参考截图时按同分辨率视觉对比。
- AI 不能可靠判断的审美、操作便利性、现场第三方或真实业务效果：移交 `human-acceptance`，明确人工核对步骤。

## 3. 执行与判定

1. 连接真实开发数据库并检查模块迁移，避免只跑 Mock 数据即宣布联调成功。
2. 沿着页面→API→权限→领域逻辑→数据库→页面显示的链路分别验证主路径和异常路径。
3. 验证前后端契约、请求/响应、错误反馈、权限边界、幂等/重复提交、数据版本和跨模块引用。
4. 验证原型：直接核对 `code/fld/` 原有页面路由、布局、组件与主题变量；除确认的局部调整，不得另起一套新UI。
5. 自动测试必须真实运行，记录执行命令、测试数据、通过/失败、日志/截图/网络证据和未覆盖项。
6. 失败标注根因方向，交 `diagnosing-bugs`；修复后必须回到实现/审查和自动联调，不可以只改一处截图就放行。

## 4. 输出与交接

统一输出到 `docs/output/06-模块迭代/<模块>/自动联调与测试记录.md`，包含 [结果模板](templates/自动测试记录.md) 要求的完整记录，并标出待人工验证场景及环境限制。

进入下一关卡的条件：**已覆盖的可自动化测试通过，未覆盖项具备可执行人工用例**。第三方接口未到位、模拟测试通过只能记录“模拟通过、真实对接待测”，不能宣称真实业务已验收。代码审查和原型一致性不是同一项检查；两者的结论分别保留。
