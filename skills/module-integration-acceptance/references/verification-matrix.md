# 可自动化与不可自动化的验证矩阵

| 维度 | AI/自动化必须验证 | 人工补充 | 失败去向 |
|---|---|---|---|
| 代码规范 / Spec | 上一步Matt code-review 检查规范、业务Spec与Diff | 技术审查仍需人工把关关键高风险取舍 | 修复→review |
| 数据库与API | 真实迁移、CRUD、事务、幂等、鉴权、错误返回、日志 | 核对业务数据语义的例外情形 | diagnosing-bugs |
| 前端原型 | 路由、布局结构、组件复用、已有CSS变量、截图差异、行为回归 | 页面体验、审美、复杂表单、不同环境交互 | 实现→联调 |
| 第三方 | 已提供Sandbox/接口可测的真实请求、超时与异常 | 客户正式对接、真实授权和现场结果 | 阻塞/返工 |
| 角色场景 | 登录、查询、提交、退回、条件展示等脚本覆盖 | 审批/核算是否符合业务角色预期 | human-acceptance |
| 性能 | 可运行基线指定的负载验证 | 现场资源与客户可感知延迟 | 后续NFR验证 |

先检测现有框架；需要补Playwright/API自动化时可借鉴 BMad `bmad-qa-generate-e2e-tests` 的“识别既有工具→API/E2E覆盖→运行测试→未覆盖汇总”，但本项目不能直接依赖BMad安装环境。
