# S05 数据库总体设计：整体规则 → 数据流程 → 表/字段/关系

## 目标与边界

**内部Grill按需启动**：遇到共享数据身份、状态或写入 Owner、删除历史语义的真实阻断性冲突时，先对照已批准项目基线、整体架构和存量Schema，再按需调用 Matt 原版 `grill-with-docs` 澄清并记录裁定。没有未决问题时跳过，不重复询问已确认事实，不修改 Matt 原版文件。

**唯一目标**：在分模块开发之前，定出全项目共用的**数据骨架**——规则、关键数据流程、核心表与核心字段及关系，使各模块不再自造客户、项目、设备、订单、审批等身份与数据权威。

**这是数据库设计，用表、字段、键、关系说话**：
- 组件、协议、消息编排、时序交互＝S04；此处只引用其结论（Owner、状态权威、链路名），不重画。**关键数据流程一律以表为主体来画**（每一步都看得出读写了哪张表）。
- 完整字段字典、辅助表、索引清单、建表 DDL＝S09/S12；此处只锁**核心**。**不写详细设计**（接口、方法、类、参数、报文、组件时序）。
- 正文只写**结论**，不写「来源/依据」列（证据在评审时给）。
- **章节要求编号**（1、1.1、2…）；**规则/条目本身不加代号**（不写 A1/①②/R01 之类）。

**成文章节（按序）**：

1. 整体数据规则——按固定清单逐条给出本项目结论，每条 1–2 句。
2. 关键数据业务流程——先一张图划分数据域，再逐域以**表**为主体画关键数据流程。
3. 分库分表设计——独立成章；需要时给完整设计。
4. 核心表、核心字段与关联关系——核心表清单 → 逐表核心字段 → ER 图与关系契约。
5. 存储与容量；6. 数据安全、生命周期与迁移支撑；7. 全局冻结与模块交接。

## 输入（只读，不写进产物）

1. 递归读 `docs/input/` 相关需求、工程、环境、对接与新增类别；读 `docs/output/01-项目基线/项目基线.md` 与已批准 `docs/output/02-整体架构/整体架构设计.md`（取 Owner、关键链路、状态权威、存储拓扑、架构冻结）。
2. 扫真实 `code/` 已有 DDL/迁移/Entity/Mapper 及框架公共表（账号、角色、组织、字典、日志）；存在者先复用并记录；不可读时注明未核验，不假装扫过、不另造第二套公共表。
3. 继承 `GLOSSARY.md` 与 ADR。
4. 缺失/冲突时给有依据的推荐与取舍，并列入待裁定；已确认的不重问；需改 S04 组件或状态 Owner 时退回 S04。

## 跨域只读与权威边界

跨域驾驶舱或聚合查询即使不写入交易库，也应明确数据Owner、被引用核心表、读取契约、权限/租户隔离、数据时效及只读约束。查询聚合不拥有被引用业务对象的权威状态，未经批准不得为了报表再建立第二套主表或暗中回写原业务库。

## 三核心执行

### 核心一 · 整体数据规则

按 [`references/rule-catalog.md`](references/rule-catalog.md) 的固定清单逐条填**本项目结论**（命名与键、质量与时间、生命周期与一致性、隔离/存储/演进、按触发的项目专项）。

- 规则就是规则：一行一条、1–2 句写重点；只写结论值，不写来源/依据/检查方式，不加代号。
- **固定命名约定**：`tb_`＝主数据/配置/实时快照、`tr_`＝关系表、`tl_`＝流水/日志/历史；**新增业务表**默认落到其中一个前缀；既有框架/第三方表（如 `sys_user`）维持原名和键模型，记录复用边界，不建同义表。
- 未触发写「不适用」；每条给冻结级别 A/B/C。

### 核心二 · 关键数据业务流程

**其一，数据域划分用一张图。** 画一张 Mermaid 图（节点＝数据域，边＝域间关联并标注连接键与方向）。图下**一句话**写依据与作用。域划分依据（详见 [`references/three-core-contract.md`](references/three-core-contract.md)）：

- 一个域＝**一族同生命周期的核心对象**，以「**权威写方 / 保留边界 / 一致性边界**」判定；
- **关系表（`tr_`）不单独成域**，归入它服务的对象族所在域；
- 框架对象族与其业务扩展表服务同一对象族时**同域**（域内按表标注写方）；
- **域数保持精简**，能合则合；只有对象族、保留或写方边界确实不同才独立成域。

**其二，逐域以表为主体画流程。**
- 流程图节点直接写**表名并在括号里给一句话释义**（如 `tb_gateway（设备档案）`）。**不要**另起一张「流程图用到的表」清单——释义就在用到处。
- 每条流程必须能一眼看出涉及哪些表：**流程图画表名**，并配一张**表动作矩阵**（每行一步，列为：涉及表、写/读、字段/状态变化、写入 Owner、一致性/异常）。**控制类、状态机类流程同样按表来画**——状态迁移处标注写入了哪张表。
- 只讲数据怎么产生/变化/归档；不画组件交互、协议、报文、类与方法（那是 S04/S09）。

### 核心三 · 核心表、核心字段与关联关系

先按统一业务术语定核心对象/数据域，再定实体是否需独立核心表（不把菜单当表、不因多 Worker 拆多库）。入选条件至少符合其一：**跨模块共享身份/关键引用；主业务闭环核心状态/版本；高成本不可逆历史/审批/计量事实；关键外部数据关联标识**。框架已有表标「复用」。

交付三件，顺序固定：**核心表清单** → **逐表核心字段**（字段名/类型/单位精度/业务含义/必填/唯一/状态/引用）→ **ER 图与关系契约**。

**ER 要好懂**：用**便于阅读的分域小图**（每域建议 2~6 张表；确实只有1张或超过6张时据实调整）一张 Mermaid `erDiagram`）＋一张关系契约表；每条关系写成 `主体表.字段 —(基数)→ 被引用表.字段`，并说明删除/历史引用约束。不把所有表挤进一张大图。

### 第三章 · 分库分表设计（独立成章）

判定是否分库/分表/分区，给出证据与**量化触发条件**。**需要时给出完整设计**，写到可直接落地：分的方式、**分片键**与分片表清单、**每个分片表的表结构**（分片键列、唯一键含分片键、表名后缀）、路由方式、全局唯一 ID、跨片查询与聚合、扩容再平衡、与主从/备份恢复的关系。不需要时写「暂不分库分表」＋触发条件；高吞吐时序表可先按时间做 MySQL RANGE **分区**（写清分区列与表结构变化）。

### 双向核验

从流程反推表/字段与关系，再从每张核心表反查业务场景与 Owner；出现「关键流程无落表」「核心字段无使用证据」「同一权威身份两处可编辑」「版本历史无法回溯」时改好再送审。产出「规则、流程、表字段、下游」映射核验表。

### 支撑维度

存储/实例/Schema 映射、容量与访问模式、安全/归档/备份/恢复与迁移兼容；服务于三核心，不替代核心模型。

## 成品、审核与冻结

用 [`assets/data-architecture-template.md`](assets/data-architecture-template.md) 按七章编写，用 [`references/data-boundary-gate.md`](references/data-boundary-gate.md) 做两轮评审（第一轮：项目经理＋技术负责人核业务与三核心完整性；第二轮：技术总监＋开发负责人核可实施与上下游一致性）。审核是过程，**不产出独立文件**，结论并入正文最后章。

冻结：A＝跨模块核心键/权威/状态版本（变更需技术总监审批并同步 S04/S09）；B＝命名/精度/隔离/迁移等全局规则；C＝模块局部字段/辅助表/普通索引交 S09。

**固定输出**：
- `docs/output/03-数据库总体/数据库总体设计.md`

仅确需新术语/高成本取舍时更新 `GLOSSARY.md`/ADR，不强制生成。

**数据约束的边界条件（F05/F10/F24）**：软删除不能把 `UNIQUE(tenant_id, code, is_deleted)` 当通用解决方案；两次删除同编码仍会撞唯一键。应根据目标数据库版本和保留要求使用可验证的“仅有效行唯一”机制、删除时修改归档键或不可变墓碑键，必须覆盖“建→删→重建→再删”测试。既有 `sys_*` 等框架表及复合键先兼容而非复制；事件时间保存标准化时间的同时，必要时保留来源时区/offset 与设备原时间，避免跨时区语义丢失。
