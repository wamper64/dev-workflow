# S05 数据库总体设计：整体规则 → 核心数据流程 → 核心数据结构

## 1. 目标与分工

**唯一目标**：在分模块开发之前，确定所有模块共同遵守的数据设计规则、关键数据生命周期，以及全局核心表/核心字段/关联关系，使模块不再各自创造客户、项目、设备、订单、审批等身份和数据权威。

**三个不可缺少的核心（按此顺序设计，必要时反向修正）**：

1. **整体数据规则**：数据库/存储责任、命名与主键、业务唯一性、时间/精度、状态/版本、历史与删除、权限隔离、数据Owner、迁移/容量/备份等跨模块必须遵守的规则。
2. **关键数据业务流程**：以S04批准的端到端业务链为上游，逐条画**数据视角**的产生/接收→校验/去重→持久化→状态/版本变化→跨域引用→归档/追溯与异常恢复。说明写入Owner、权威来源、同一事务范围或最终一致性、重复/乱序/重试时的数据结果。**不重画由哪个组件执行业务判断、用何协议发送消息等S04已有技术链路**。
3. **核心数据结构**：形成全局核心对象和数据域清单、核心表清单、**必须提前锁定的核心字段（具体字段名、候选/已批准数据类型、是否必填、唯一/身份/状态/版本/引用规则）**、表间基数和删除/修改影响、核心ER图。必须能用结构承接每条关键数据流与全局规则。

**支撑维度**：数据库/Schema和其他存储的映射、真实容量与访问模式、分库分表取舍、数据安全/归档/备份/恢复与迁移兼容。它们服务于三核心，而不是替代核心模型。

## 2. 输入及可信度

1. 递归读取`docs/input/`全部相关需求、工程、环境、对接与新增类别，已确认项目/模块PRD、原型页面/业务动作、第三方与设备数据合同；读取`docs/output/01-项目基线/项目基线.md`与**已批准**的`docs/output/02-整体架构/整体架构设计.md`，尤其组件Owner、关键业务链路、交互/状态权威、架构冻结。
2. 检查实际`code/`中已有数据库迁移、DDL、Entity/Mapper/持久层及框架提供的账号、角色、组织、字典、日志等公共表。存在的结构先复用并记录真实证据；不可访问时注明未核验，不得假装扫描过，不得另造第二套公共表。
3. 继承已有`GLOSSARY.md`和ADR（如有）。识别真实存储产品/版本、用户/容量/保留约束，严禁把报价案例或公司常用技术栈当成所有项目的确认事实。
4. 对决定全局表身份、跨域Owner、数据丢失或不可逆历史的缺失/冲突，给出**有依据的推荐、替代方案、取舍影响**；必要时在本Skill内调用`grill-with-docs`，只向相关负责人确认实际缺口。已在PRD/S03/S04确认的内容不重问。若需改变S04组件或状态Owner，退回S04审定后才继续。

## 3. 三核心执行流程

### 3.1 核心一：整体数据规则

按`references/three-core-contract.md`逐项判定**通用规则 + 按业务触发的专项规则**，每条规则填写：来源事实或推荐、裁决值/适用对象、检查方式、是否全局冻结、例外审批人。

- 身份与关系：通用主键策略、业务唯一身份、跨表/跨域引用策略、父子关系删除影响；不得默认跨库物理外键。
- 存储规范：沿用批准DB类型与版本，规范命名/时间与时区/金额计量精度/null语义/状态枚举、软删除与历史不可覆盖边界；框架已有约定优先。
- 权威与一致性：唯一写入Owner、外部只读/同步来源、事务或最终一致性边界、幂等/并发冲突、历史版本/审计。
- 安全与生命周期：租户/组织/项目数据隔离、敏感字段保护、数据保留起点与删除、附件/缓存/原始数据权威、备份恢复。
- 变更与能力：字段和Schema兼容演进、容量读写与扩容阈值；不为“以后可能用到”无依据地选分库分表。
- Web/IoT/计量/审批/长任务/Agent/第三方仅在PRD真实触发时加具体规则，未触发列为不适用，不自动引入时序库或多存储。

### 3.2 核心二：关键数据业务流程

从**S04已经批准**的主业务闭环及差异化数据路径中选取主要链路：创建/确认、设备或第三方接入、状态变更与审批、重试或重算、生成归档、历史查询等（按项目实际适用）。普通同构CRUD可合并，不是每个页面一张图。

每条链路输出**数据生命周期图 + 数据动作矩阵**，逐步写清：触发业务场景/S04链路 → 输入数据与权威来源 → 创建/更新/引用的核心数据对象 → 写入Owner/存储落点 → 状态与版本变化 → 幂等/一致性/失败后数据后果 → 留存/历史终态。关键状态另画状态转换图或状态表。明确“数据已接收”“业务状态已确认”“对外动作成功”是否为不同事务/阶段。

**双向核验**：从关键数据流程推导所需表/字段、关系；从每个全局核心表反查真实业务流程和数据Owner。发现流程无存储归属或核心表无场景依据，补齐或删除；若产生组件/协议新需求，先回退S04。

### 3.3 核心三：核心表、核心字段与关联关系

先按统一业务术语确定**核心对象/数据域**，再确定实体是否需要独立核心表，不能把模块菜单当数据表，也不因有多个Worker便拆出多个数据库。

核心表入选条件至少符合其一：**多个模块共享的权威身份/关键引用；贯穿主业务闭环的核心状态/版本；高成本不可逆的历史/审批/计量事实；关键外部数据关联标识**。框架已存在的表标记“复用”，不是重新设计。

对每张核心表交付：
- **表级契约**：表名、业务对象、写入Owner/读方、既有/新增、核心状态/数据事实、留存删除约束、来源证据。
- **核心字段契约**：字段名、数据类型（基于已确认存储版本；待裁决明确标记）、作用/业务口径、必填与空值、唯一性/身份/状态/版本/关键业务计算或外部关联约束、引用对象和写入方。不能只写`id/status`等空泛名称；要说明全局意义、不可突破条件。
- **关系契约和ER图**：父子表1:1/1:N/N:M、主/外键或逻辑引用、跨域Owner与删除/变更后的引用完整性；多对多按实际关系建模，不擅自设级联物理删除。
- **贯通校验**：每个关键流程步骤能落到相应核心表/字段；每个共享身份有唯一权威；重要状态和版本有稳定追溯依据；已批准的组件和数据Owner没有被改变。

**设计深度边界**：这里允许且必须定义**全局关键业务字段及必要类型/唯一/引用约束**；但不穷举每张表所有非核心字段、不输出全部辅助表/详细索引清单、不生成建表DDL、Mapper或Entity。模块S09继承和补全，编码S12形成版本化SQL。若后续模块发现核心结构不合理，先评估是否属于冻结变更，再更新S05和受影响模块，而非悄悄加第二套核心表。

### 3.4 支撑：物理存储与运行演进

画**数据域/核心表→已批准存储产品/实例/Schema/对象存储/缓存/外部系统**映射（数据域≠实例）；在已有资源基线上记录原始数量、增长速率、保留周期、行/索引/附件估算假设、主要读写路径和峰值，不能仅凭行数假装得到准确磁盘容量。决定是否采用单库、独立库、分片及触发指标。记录备份覆盖、恢复目标及验证前提、历史归档/删除、Schema前向兼容与回退边界；不在此配置真实服务或执行迁移。

## 4. 成品、审核与冻结

使用`assets/data-architecture-template.md`按六章编写，并用`references/data-boundary-gate.md`进行两轮评审：

- **第一轮·业务与三核心完整性（项目经理+技术负责人）**：规则是否对应PRD/基线、核心数据流程是否覆盖S04实际关键场景、表与字段是否真实支撑流程/ER与历史追溯，缺失不能凭猜测标已通过。
- **第二轮·全局数据可实施性（技术总监/开发负责人）**：选一个跨模块关键链路，沿“规则→数据步骤→核心表/字段→关系→Owner/存储→异常/恢复→S09继承点”走通；核对真实已有工程、容量存储、冻结清单与上游架构没有冲突。

冻结A级：全局共享核心表的身份/关键引用/权威、关键状态/版本语义、存储权威与跨模块一致性策略，变更需技术总监审批并同步S04（如有影响）和S09；B级：命名/通用精度/迁移/安全等全局规则须兼容修改；C级：模块局部字段、辅助表和普通索引交S09自主深化。所有冻结项须给出**允许扩展、不允许的变更、验证依据**；不能把整张核心表永远锁死。

**固定输出**：
- `docs/output/03-数据库总体/数据库总体设计.md`
- `docs/output/03-数据库总体/数据库设计审核.md`
- 仅确需新术语/高成本取舍时更新`GLOSSARY.md`/ADR，不强制生成。
