# 开发环境部署

## 唯一目标

**先由人填写环境信息表，再执行确定的部署步骤**。不是让AI凭经验指定Windows目录，也不是先写一份“建议用Docker”的方案就算完成。

### 1. 输入先决条件

- `docs/input/环境资料/开发环境信息.md`：由项目研发导航**右侧可填写的环境表格**生成，用户负责核对事实。其他现有 `docs/input/` 资料仍须按需读取。
- `docs/output/01-项目基线/项目基线.md`：版本与资源约束。
- `docs/output/02-整体架构/整体架构设计.md`：需要部署的真实组件与调用关系。
- `docs/output/03-数据库总体/数据库总体设计.md`：数据库/存储与分库分表等决定。
- `code/` 现有前端，`code/` 既有后端。

**禁止将测试机IP、宿主系统、服务版本、端口、数据目录和可操作权限猜成已经存在的事实；不得采集或在Markdown中输出密码、Token和私钥。**

### 2. 按顺序部署（严格依表执行）

1. **先读填写表**：检测缺失项；确定目标宿主系统、资源、已装依赖及版本、可用端口/路径/网络、可用权限。
2. **核对已确认架构**：从整体架构组件清单导出开发环境需要的数据库、缓存、消息、知识服务、业务API、代理等适用项；没有需求的不强制部署。
3. **做部署差异计划**：逐项标注“已存在可复用 / 缺失需安装 / 未获授权不能动”；提交明确的版本、命令、路径、依赖和失败停止条件。
4. **按依赖顺序执行**：得到用户允许操作的前提后，部署基础目录及网络→数据库/缓存等必需组件→数据库初始化/迁移准备→环境与基础依赖的就绪核验（如本轮尚无可发布应用则只预留目录和接口）；每一步需检查退出码并决定是否继续。
5. **真实验收**：通过运行命令、健康接口、数据库连接、权限与API/前端页面联通获取真实执行证据；需要第三方且未到位则记录阻塞，不能将Mock当正式通过。
6. **记录和恢复**：将已执行/失败/未执行、命令（脱敏）、输出和修复指引写入部署记录，列出下次可重复执行的方式与回滚方案。

## 输出

- `docs/output/04-开发环境/部署步骤与执行记录.md`，采用 [模板](assets/output-template.md)。
- 需要时产生 `deploy/dev/docker-compose.yml`、`deploy/dev/.env.example`（不得含真实密钥）。
- 不擅自修改用户填写的 `docs/input/环境资料/开发环境信息.md`。

## 审核

先完成环境表，未经明确授权不操作可能覆盖现有数据的组件。只有真实执行命令、版本、端口、数据库连接及前后端联通检查完成才标通过，未执行的步骤保持待执行。用户可持续更新右侧表格并重新导出。
