# 模块拆分门禁（业务职责与生命周期为主判据，借鉴Matt to-tickets的交付切片、阻塞边与粒度确认）

检查顺序：**角色×场景发现候选 → 业务职责和核心对象生命周期决定拆合 → 权威Owner与架构校验 → 依赖DAG → 人工审核**。

| 维度 | 应检查的实际证据 | 失败处理 |
|---|---|---|
| 需求覆盖 | 已确认PRD中每个角色×核心场景都有来源与可验收结果，且仅有一个主责模块，可有协作模块 | 补遗漏、删无依据或重复功能、改归属冲突 |
| 业务职责 | 每个模块能说明独立或紧密关联的业务目标、负责什么及不负责什么，不能只列CRUD页面 | 目标高度相同且维护责任一致时考虑合并；职责独立时考虑拆分 |
| 核心对象与生命周期 | 记录核心对象、创建/变更/完成或关闭状态及唯一权威Owner；拆合决定与对象生命周期有证据关联 | 同一生命周期被无依据割裂时合并；独立对象/状态责任且可验收时可拆分 |
| 业务规则与独立验收 | 列明共享或独立规则，以及拆成两个模块后是否都能交付可观察业务结果 | 无独立业务价值的碎片回并；职责过杂、不同规则与独立结果可适当拆分 |
| 纵向业务交付 | 每个模块至少有一条角色触发、穿过已有界面和业务能力、到结果的闭环 | 不能只叫“前端模块”“数据库模块” |
| Owner一致性 | 模块对应已批准架构组件/数据域的权威Owner，可写对象/关键状态不出现双Owner | 归属不清先澄清；改变骨架必须返回S04/S05 |
| 粒度禁止项 | 不把菜单、页面、表、Controller、代码目录、前后端层、单张Ticket或既定数量直接当拆分单位 | 按职责、对象生命周期与场景重新判定 |
| 模块与Ticket粒度 | 模块可包含多个开发Tickets，本阶段不要求单个上下文即可编码 | S07不发布实现Ticket，S11再调用官方to-tickets |
| Blocked by | 真正强阻塞列出模块ID、必须先交付的业务能力/数据、阻塞原因及解除条件 | 将建议顺序与真实阻塞分离 |
| 可并行契约 | 仅依赖稳定接口的数据/模块不被错误标记为必须等上游全部完成 | 明确契约冻结和最终真实集成验收差异 |
| 第三方/环境阻断 | 真实接口、授权、设备与环境的阻塞独立列出，Mock不能冒充真实验收 | 标记阻塞及其解除条件 |
| DAG无环 | 模块依赖图无环；如有环则回溯Owner、共享契约和真实阻塞关系 | 不允许靠删除真实阻塞边“修图” |
| 已有工程复用 | 模块场景与 `code/` 原型页面及现有代码映射，前端沿用原型样式 | 回到已确认PRD、架构和真实代码纠正 |
| Matt式Quiz | 用户逐项确认粒度、拆/合理由与依赖；项目经理审核业务，技术总监审核架构/Owner | 未批准只能提交候选模块池 |

## 拆合裁决记录（每个争议必填）

| 候选能力/模块 | 共同或不同的业务目标 | 核心对象/状态Owner | 能否分别验收 | 合并/拆分/待澄清 | 依据（PRD场景/原型/架构） |
|---|---|---|---|---|---|

**红线**：场景差异、页面差异或数据库表差异都不能单独成为拆分结论；共享一张表也不能单独成为必须合并的结论。数据权威归属按已审定总体数据库设计，不能在这里擅自改写。

项目模块与开发Tickets的关系：**S07模块池→S08选择本轮模块→S09详细设计→S10模块Spec→S11原版to-tickets发布单上下文实现任务**。
