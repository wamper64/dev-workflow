# 模块拆分门禁（参考Matt to-tickets的交付切片、阻塞边与粒度确认）

| 维度 | 应检查的实际证据 | 失败处理 |
|---|---|---|
| 需求覆盖 | 已确认需求基线中的每个角色×核心场景，至少对应唯一主责模块 | 补遗漏、删冗余、改冲突 |
| 纵向业务交付 | 每个模块可以描述角色如何触发、经过哪些已有界面/业务能力、产生什么可观察结果 | 不能只叫“前端模块”“数据库模块” |
| Owner一致性 | 模块能对应整体架构组件与数据域权威，重要状态归属明确 | 若涉及更改骨架，返回S04/S05 |
| 模块与Ticket粒度 | 模块可能包含多个Tickets；本阶段只拆模块，不要求“单个上下文即可编码” | 不在S07提前发布实际开发Ticket |
| Blocked by | 真正强阻塞明确列模块ID、被阻塞的原因、解除条件 | 将建议顺序与真实阻塞分离 |
| 可并行契约 | 仅依赖稳定接口的模块不被错误设为必须上游完成 | 明确接口冻结与最终真实集成验收差异 |
| 第三方/环境阻断 | 真实接口、授权、设备等要求与DAG分开列，不能把Mock视为已验收 | 标记受阻、安排先决条件 |
| DAG无环 | 模块依赖图无环，环如存在有清晰Owner/共享契约调整依据 | 不允许通过删除真实阻塞边“修图” |
| 已有工程复用 | 与`code/`原型/页面/业务代码映射对应，不新造UI和重复公共能力 | 回到真实代码和PRD纠正 |
| Matt式Quiz | 用户对过大/过小、blocked by、拆分/合并逐项裁定，项目经理与技术总监明确审核 | 没有确认则只产生候选池 |
