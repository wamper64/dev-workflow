# 模块拆分门禁（业务职责与生命周期为主判据，借鉴Matt to-tickets的交付切片、阻塞边与粒度确认）

检查顺序：**角色×场景发现候选 → 业务职责和核心对象生命周期决定拆合 → 权威Owner与架构校验 → 依赖DAG → 人工审核**。

| 维度 | 应检查的实际证据 | 失败处理 |
|---|---|---|
| 需求覆盖 (R1) | 已确认PRD中每个角色×核心场景都有来源与可验收结果，且仅有一个主责模块；前端每个页面/功能及无页面能力唯一归属一个主责阶段 | 补遗漏、删无依据或重复功能、改归属冲突；结论落为《项目模块清单》覆盖表 |
| 模块资格 (R2) | 通常负责对象/状态；独立可验收的跨域聚合、无页面事件/定时/Agent能力允许明确的责任模块，页面壳不独立 | 无独立验收目标则并入；独立聚合/系统能力须写主责与场景证据 |
| 模块数量 (R5) | 10为评审阈值；超出需提供独立职责、Owner、验收依据及项目经理/技术总监裁决 | 不得只为减数合并真实边界；若确有客户批准硬上限且无法合理合并则阻断并提交范围取舍 |
| 功能级覆盖 (R7) | 页内跨阶段功能已在所属阶段点名（如"人员管理·分配电站"）；被剥离功能的页在本阶段标注"（不包含 X）"，范围无歧义；概览/统计页按数据来源分摊 | 漏点名即补；整页与其页·功能范围重叠或缺排除注记即改 |
| 第三方对接覆盖 (R1) | 架构外部对象清单中的每个系统都在某阶段"第三方对接"列归位一次，首次对接与后续复用已区分；未默认塞进末尾阶段 | 漏归位即补入其真正对接阶段 |
| 业务职责 (R1/R3) | 每个模块能说明独立或紧密关联的业务目标、负责什么及不负责什么，不能只列CRUD页面 | 目标高度相同且维护责任一致时考虑合并；职责独立时考虑拆分 |
| 核心对象与生命周期 (R1/R3/R4) | 记录核心对象、创建/变更/完成或关闭状态及唯一权威Owner；拆合决定与对象生命周期有证据关联 | 同一生命周期被无依据割裂时合并；独立对象/状态责任且可验收时可拆分 |
| 业务规则与独立验收 (R3/R4) | 列明共享或独立规则，以及拆成两个模块后是否都能交付可观察业务结果 | 无独立业务价值的碎片回并；职责过杂、不同规则与独立结果可适当拆分 |
| 纵向业务交付 (R1) | 每个模块至少有一条真实触发（页面/设备/定时/外部事件/Agent）到可观察结果的闭环 | 不能只叫“前端模块”“数据库模块” |
| Owner一致性 (R6) | 模块对应已批准架构组件/数据域的权威Owner，可写对象/关键状态不出现双Owner | 归属不清先澄清；改变骨架必须返回S04/S05 |
| 粒度禁止项 (R1) | 不把菜单、页面、表、Controller、代码目录、前后端层、单张Ticket或既定数量直接当拆分单位 | 按职责、对象生命周期与场景重新判定 |
| 横切能力归属 (R9) | 通知/文件/字典/审计/权限等横切或共享能力未被无依据地单列成模块；无独立业务目标与自有对象者作为架构共享组件或并入其服务的模块 | 无自有对象且无独立业务目标者并入相应模块，或标记为架构共享组件 |
| 模块与Ticket粒度 | 模块可包含多个开发Tickets，本阶段不要求单个上下文即可编码 | S07不发布实现Ticket，S11再调用官方to-tickets |
| Blocked by | 真正强阻塞列出稳定module_key（展示序号可变）、必须先交付的业务能力/数据、阻塞原因及解除条件 | 将建议顺序与真实阻塞分离 |
| 可并行契约 | 仅依赖稳定接口的数据/模块不被错误标记为必须等上游全部完成 | 明确契约冻结和最终真实集成验收差异 |
| 第三方/环境阻断 | 真实接口、授权、设备与环境的阻塞独立列出，Mock不能冒充真实验收 | 标记阻塞及其解除条件 |
| DAG无环 | 模块依赖图无环；如有环则回溯Owner、共享契约和真实阻塞关系 | 不允许靠删除真实阻塞边“修图” |
| 已有工程复用 | 模块场景与 `code/` 原型页面及现有代码映射，前端沿用原型样式 | 回到已确认PRD、架构和真实代码纠正 |
| Matt式Quiz | 用户逐项确认粒度、拆/合理由与依赖；项目经理审核业务，技术总监审核架构/Owner | 未批准只能提交候选模块池 |

## 拆合裁决记录（运行内过程，不写入《项目模块清单》）

《项目模块清单》覆盖前端页面/功能及无页面业务能力（`序号 | module_key | 阶段 | 阶段模块/交付能力`）；以下裁决仅在运行内进行，用于得出该表的模块归属与阶段顺序。

| 候选能力/模块 | 共同或不同的业务目标 | 核心对象/状态Owner | 能否分别验收 | 合并/拆分/待澄清 | 依据（PRD场景/原型/架构） |
|---|---|---|---|---|---|

**红线**：场景差异、页面差异或数据库表差异都不能单独成为拆分结论；共享一张表也不能单独成为必须合并的结论。数据权威归属按已审定总体数据库设计，不能在这里擅自改写。

项目模块与开发Tickets的关系：**S07模块池→S09选择本轮任务、依赖门禁与详细设计→S10模块Spec→S11原版to-tickets发布单上下文实现任务**。

**稳定引用门禁**：module_key 唯一且不变；排序变化不影响 Tracker、依赖DAG、模块设计与历史签收。原型识别先核实路由/权限/动态菜单的真实注册机制。
