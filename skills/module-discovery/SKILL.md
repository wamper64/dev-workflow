# 全项目模块识别与划分（基于 Matt Tickets 改造）

## 1. 目标与粒度边界

把已确认的需求基线转化为**整个项目的可分批交付业务模块池**，确定模块边界、角色×核心业务场景、既有页面、系统组件/数据Owner归属以及前置依赖，供下一步选择本轮模块。

本Skill**学习并改造**Matt `to-tickets` 的三个关键机制：

1. **Tracer bullet / 纵向交付**：每个模块至少有一条贯穿实际业务使用路径的可验收场景，不把全部前端、全部后端、全部数据库分别拆成独立业务模块。
2. **Blocking edges / 阻塞依赖**：显式列出什么必须先完成、什么只需接口契约确认就能并行；不以“建议先做”冒充强依赖。
3. **Quiz / 人工校准粒度**：向项目经理与技术总监展示模块名称、实际交付、前置依赖，逐项确认过大/过小、阻塞边是否必要、应该合并或拆开哪些模块。

**与Matt原版的区别必须保留**：原版 `to-tickets` 面向已经确定的计划/Spec产出**适合单个新上下文完成、可发布到Issue Tracker的开发Tickets**。项目模块往往包含多轮设计与多个Tickets，不能伪装成单个可执行Ticket。因此**S07不调用原版发布全项目开发Tickets**，而是在模块级运用同样的可交付与依赖思想；正式单任务Tickets由S11在本轮模块Spec确定后**完整调用Matt原版**。

## 2. 输入（必须从现有资料提取，不能猜模块数）

- 递归读取 `docs/input/` 下需求、工程、环境、对接及新增类别的全部相关资料；尤其是**已确认需求基线的项目PRD、模块PRD、角色×核心场景和现有页面/菜单映射**，已有映射直接继承，不重新扫描生成一份。
- `docs/output/01-项目基线/项目基线.md`：技术、性能、资源、数据留存等全局约束。
- `docs/output/02-整体架构/整体架构设计.md`：已审定组件/交互职责、身份/状态Owner及系统边界。
- `docs/output/03-数据库总体/数据库总体设计.md`：已审定数据域与数据Owner、存储/分库策略。
- 实际存在的 `code/deploy/single-node-docker/初次部署配置-<环境名称>.md` 与 `部署结果README-<环境名称>.md`：逐环境核对授权、执行结果与受阻条件；仅有配置不能宣称已经部署。
- `code/` 已存在的实际前后端/Agent/第三方工程：仅定位可复用页面、组件、API与代码模块，不修改代码，也不审查现有框架的质量。
- 如已有 `GLOSSARY.md` 与 `docs/adr/`，继承名称和已确认决定。

## 3. 拆分流程与判定依据（项目模块级，不发布开发Ticket）

### 3.0 固定拆分判据与优先级

**主判据是业务职责与核心业务对象的完整生命周期**，角色×核心场景用于发现候选及验证覆盖；架构和数据Owner用于校验；依赖用于确定实施关系，**不能反过来凭依赖数量或实施顺序决定模块数量**。

| 顺序 | 依据 | 在本阶段的作用 |
|---|---|---|
| 1 | 角色×核心业务场景 | 从已确认PRD发现业务能力，确保一个完整业务结果可被观察和验收 |
| 2 | 业务职责边界 | 判断能力是否围绕同一业务目标、规则和责任聚合 |
| 3 | 核心业务对象及状态生命周期 | 判断由谁负责创建、变化、终结与追溯，明确权威Owner |
| 4 | 已批准整体架构与数据库总体 | 校验组件、数据域、状态Owner与现有代码复用，不借模块划分重画架构 |
| 5 | 模块依赖关系 | 确定强阻塞、契约依赖和外部阻塞，得出DAG及可实施候选 |

不以单个菜单、页面、数据库表、Controller、代码目录、前后端技术层或单张Ticket直接命名一个业务模块。业务模块边界**不等于**独立服务、Worker或部署单元边界。

**拆分规则（按序应用，前条优先）**

| # | 规则 | 判定 |
|---|---|---|
| R1 | **主判据** | 模块围绕**一个业务目标**＋**一组紧密关联的核心业务对象及其生命周期**；不按菜单/页面/表/代码目录/前后端层或预设数量拆分 |
| R2 | **资格线** | 通常模块权威负责业务对象/状态；**跨域聚合、查询产品、无页面的事件/批处理/Agent能力**若具有独立业务目标、确定责任方与可独立验收结果，可作为独立责任模块；若仅为页面壳或共享组件则归入已有模块 |
| R3 | **合并** | 同一业务目标＋同一或紧耦合的对象生命周期＋同一 Owner → 合并 |
| R4 | **拆分** | 对象与状态权威独立、生命周期独立、且可分别验收 → 拆分 |
| R5 | **数量评审阈值** | **10 个为粒度评审阈值，不是强制合并上限**；超过10需说明独立职责/Owner/验收依据，并由项目经理与技术总监评审；不得只为数量达标合并真实边界 |
| R6 | **一对象一 Owner** | 同一可写对象/关键状态只有一个权威 Owner，跨模块仅经契约协作 |
| R7 | **页面是容器** | 页内跨阶段功能点名、被剥离页加"（不包含 X）"、概览页按数据来源分摊（§3.2.1） |
| R8 | **领域≠模块** | 同域不构成合并理由（同为运营域的流量卡与固件仍可分），跨域也不构成拆分理由 |
| R9 | **横切≠模块** | 通知、文件/附件、字典、审计、权限等横切/共享能力，若无独立业务目标与自有对象生命周期，作为架构共享组件或归入其服务的领域模块，不单列业务模块 |

> 冲突时以序号小者优先：R2 可推翻凭"有独立页面/能独立开发"得出的模块候选；R5 只在 R3 无解时兜底。

### 3.1 从场景发现候选业务能力

逐项读取PRD中的**角色×核心业务场景**，记录业务入口（使用已有原型页面）、触发动作、核心业务对象、状态变化、涉及组件和可观察的业务结果；同时识别权限拒绝、校验失败、驳回、重试等实际有依据的重要分支。不能把“有一个菜单/CRUD页面”视为已经得到可验收的业务能力。

在场景映射表中记录PRD或原型来源，提出**候选归属**，尚不预设模块数量。该阶段只是识别业务能力，不生成实现Ticket，也不因跨前后端、消息队列或数据库就拆成多个模块。

### 3.2 按职责与生命周期聚合、拆分并确定Owner

对每组候选场景，按以下顺序判定：

1. **业务目标与职责**：是否共同完成一个主要业务结果，适合由同一业务责任方维护？是则优先合并；目标和职责明显独立则考虑拆分。
2. **核心对象与生命周期**：是否围绕相同核心业务对象及紧密关联的状态流转（创建、执行、审批、关闭、归档等）？紧密关联优先合并；对象、状态权威及变化规则独立且边界清晰才考虑拆分。
3. **业务规则与独立验收**：合并是否造成职责过杂、规则频繁相互牵制？拆开后能否分别产生真实可验收的业务结果？仅因各自能编码或有页面，不构成拆分理由。
4. **跨模块协作与数据Owner**：对每个可写业务对象和关键状态只能指定一个权威Owner；其他模块只能通过已批准的契约协作，不能各自维护第二套权威状态。每项跨模块场景指定唯一主责模块及协作模块。

每次拆/合必须写出**所依据的场景、对象/状态、职责边界、独立验收结果和决策理由**；有争议时保留候选并交审核，不用主观数量目标替代判断。

每个正式候选模块须明确：阶段序号与名称（**每个模块设稳定 `module_key`（slug，例如 `device-alarm`），并独立保留可调整的阶段序号；module_key用于 Spec、依赖、任务、验收与状态映射，不随排序更改）、做什么与不做什么、核心对象及状态Owner、主要角色×场景、现有原型/页面/代码复用点、已定架构组件和数据域、可验收业务结果。一个模块可以跨多个页面和组件，一个页面也可以消费多个模块；**模块只定义业务归属，不擅自新增独立系统、数据库或部署服务**。

**模块数量评审阈值（不是上限）**：全项目模块数以实际业务职责、核心对象生命周期、独立Owner与可验收边界为准。超过10个时应解释为何需要独立交付，并请项目经理与技术总监复核是否存在重复职责、可合并的同生命周期子模块；**不得为凑到10个而强制合并**。例如确有12个独立且可验收的业务责任模块，就保留12个并记录评审结论。

### 3.2.1 功能级归属（页面只是容器）

模块的最小交付单元是**功能**，不是页面；一张页面可含属于不同阶段的功能。三项强制检查，用于堵住"页面交付了、页内某功能却漏做/被后置/范围不清"的缺口：

- **跨阶段点名**：页内某功能的对象/数据属于另一阶段（尤其更晚阶段）时，必须在该功能真正的阶段行点名 `页面·功能`（例：人员管理在第 1 阶段交付，其"分配电站"功能属于电站阶段，须在电站阶段行点名"人员管理·分配电站"）。否则"页面已交付"会掩盖该功能而漏做。
- **排除注记（范围无歧义）**：阶段内写**整页名**即代表该页**全部功能**；若该页的部分功能已归他阶段，本阶段必须写成 `页面名（不包含 功能名）`（例："人员管理（不包含 分配电站）"）。各阶段列出的页面/功能并集 = 该页全部功能，既不重叠也不遗漏。
- **概览页分摊**：没有独立聚合合同、验收与维护职责时，以某领域数据为主的概览/统计页，其该领域部分随该领域阶段交付，不整体后置到末尾统计阶段（例：所有电站、电站概况的电站部分随电站阶段交付，设备/运行部分随设备运行阶段）。具有跨领域产品责任、统一可验收业务结果的独立驾驶舱按 R2 特例归属独立主责模块，不能被数据来源分摊规则消除。

### 3.3 按 Matt Blocking edges 建立模块级依赖DAG

为每个模块定义：

- **强阻塞（blocked by）**：下游核心场景必须依赖上游已经交付的真实能力或数据；写明上游稳定module_key（展示序号仅辅助）、必须先交付什么、原因及解除条件。仅因建议先开发上游不构成强阻塞。
- **契约依赖**：约定稳定接口、模型和测试替身即可并行开发；明确依赖的具体契约以及何时必须完成真实集成验收。
- **环境/第三方阻塞**：需要账号、真实设备、授权或测试环境；和模块DAG依赖分开说明，落盘载体为《模块依赖关系》的「第三方与环境阻塞」一节。
- **无依赖**：可以从本轮选择阶段开始考虑。

给出边标注依赖内容的 Mermaid DAG，以及**按阶段分节的《上游依赖 / 交付范围 / 下游》**（每节写清三项；交付范围含能力、核心对象与 Owner、页面、第三方对接与可验收结果，不只是页面）；检测循环依赖，将公共Owner/共享契约拆清而不是偷偷删除边。区分“可以开发”与“可以真实验收”，模拟数据不能当作第三方验收完成。

### 3.4 Quiz：项目经理与技术总监审核模块粒度

**像Matt原版to-tickets一样用可理解的列表向用户提问，但提问对象是模块不是Ticket。** 每个模块展示：

`模块名称 | 主要职责与非职责 | 核心对象/状态Owner | 角色×场景与可验收结果 | 拆/合依据 | blocked by与契约依赖`

至少确认：**模块数是否超过10**（超阈值应给职责与验收理由，经项目经理和技术总监确认；不得强制合并）；模块是否过粗/过细；合并是否共享同一业务目标与生命周期；拆开后能否分别验收；是否有两个模块同时修改同一权威状态；强依赖是否真实阻塞；**页内跨阶段功能是否已在所属阶段点名、被剥离功能的页是否加"（不包含 X）"排除注记、概览页是否按数据来源分摊（§3.2.1）**；PRD是否遗漏、重复或多出了无依据功能；是否擅自新增独立系统。项目经理批准业务范围；技术总监批准系统组件/数据责任和依赖。未确认前只能提交候选清单，不能把草案称为已审定模块池。

### 3.5 反向校验全覆盖与对下游的交付契约

按需求基线逐项核对每个核心场景有且仅有**一个主责模块**（可有多个协作模块），检查入口、业务结果、异常分支与已有原型是否覆盖；漏项做"补"，无依据或重复功能做"删"，Owner/页面/依赖冲突做"改"。**核验结论落为《项目模块清单》覆盖表：前端每个页面/功能与无页面系统能力/异步事件/定时任务/Agent业务结果分别有唯一主责阶段，且每个外部对接对象（取自架构的外部对象清单）至少在"第三方对接"列归位一次**，并以《模块依赖关系》DAG 佐证；补删改的证据与理由保留在运行内。若拆分时发现需求本身有歧义，只记录待澄清项，不能擅自修改已确认PRD。总体组件/通信如需变更，返回S04架构复审；数据域如需变更，返回S05数据库总体设计复审。

**在S07结束后，只有模块池与模块依赖，尚无全项目可执行Tickets。** S09选择真实就绪任务、校验依赖并完成模块详细设计，S10确认本模块Spec，**S11调用未修改的Matt原版`to-tickets`并向已配置Tracker发布单上下文纵向Tickets**。这两个层级分别存储，避免全局模块列表被实现Ticket淹没。

## 4. 正式输出

- `docs/output/05-模块拆分/项目模块清单.md`：**一张覆盖表**，核心列为 `序号 | module_key | 阶段 | 阶段模块/交付能力`，项目有外部系统时增设 `第三方对接` 列。
  - **阶段**＝业务模块（可分批交付的单元，即模块池成员）；**序号**＝交付/使用顺序，**身份与登录类阶段排在最前**（先登录才能进入平台），其余按业务流转推进。
  - **阶段模块/交付能力**＝该阶段覆盖的实际前端页面/功能以及无页面后端事件、任务、跨域查询/Agent能力，允许写成 `页面名·功能名`（页内跨阶段功能）或 `页面名（不包含 功能名）`（整页扣除已归他阶段的功能），概览页的分摊部分见 §3.2.1；逐项列出，名称来自扫描确认的真实路由/菜单注册机制（单文件、多文件路由、动态权限菜单或i18n均可）；只有真实权威标题才逐字比对，示例文件名不是强制目录；同名不同页加限定（如"设备详情（概况）"与"设备详情（综合管理）"）。
  - **第三方对接**（项目有外部系统时**增设一列**）＝本阶段需要对接的外部系统及其用途，取自《整体架构设计》的外部对象清单（如 OneNET、卡商、短信、地图、视频、注册中心）。规则：**每个外部对象至少在某一阶段归位一次，首次建立接入底座/凭据的阶段须与后续复用阶段区分标注**；据此核对没有任何第三方对接被遗漏、也没被默认塞进最后阶段。
  - 用途：前端每个页面/功能有且只有一个主责阶段；写整页名即含其全部功能，页内跨阶段功能须在目标阶段点名、被剥离功能的页加排除注记、概览页按数据来源分摊（§3.2.1）——据此一眼核对**所有页面、所有功能是否被覆盖且范围无歧义**（漏项做补、重复做删、无依据做删、归属或范围冲突做改）。
  - 拆合讨论仍在运行内；但每个无页面能力必须在正式清单中列出唯一主责与可验收结果，稳定 `module_key` 必须写入正式表，Owner及依赖写入正式《模块依赖关系》；表的完整无遗漏即为覆盖核验结论。
- `docs/output/05-模块拆分/模块依赖关系.md`：模块级DAG、强阻塞/契约依赖/第三方受阻、可优先实施的模块。

**审核是过程，不产出独立文件**：拆/合与依赖评审在本次运行内执行，结论体现为覆盖表的完整与依赖表/DAG 的正确；必要时在对话内说明，不落独立文件。
