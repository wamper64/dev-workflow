# 全项目模块识别与划分（基于 Matt Tickets 改造）

## 1. 目标与粒度边界

把已确认的需求基线转化为**整个项目的可分批交付业务模块池**，确定模块边界、角色×核心业务场景、既有页面、系统组件/数据Owner归属以及前置依赖，供下一步选择本轮模块。

本Skill**学习并改造**Matt `to-tickets` 的三个关键机制：

1. **Tracer bullet / 纵向交付**：每个模块至少有一条贯穿实际业务使用路径的可验收场景，不把全部前端、全部后端、全部数据库分别拆成独立业务模块。
2. **Blocking edges / 阻塞依赖**：显式列出什么必须先完成、什么只需接口契约确认就能并行；不以“建议先做”冒充强依赖。
3. **Quiz / 人工校准粒度**：向项目经理与技术总监展示模块名称、实际交付、前置依赖，逐项确认过大/过小、阻塞边是否必要、应该合并或拆开哪些模块。

**与Matt原版的区别必须保留**：原版 `to-tickets` 面向已经确定的计划/Spec产出**适合单个新上下文完成、可发布到Issue Tracker的开发Tickets**。项目模块往往包含多轮设计与多个Tickets，不能伪装成单个可执行Ticket。因此**S07不调用原版发布全项目开发Tickets**，而是在模块级运用同样的可交付与依赖思想；正式单任务Tickets由S11在本轮模块Spec确定后**完整调用Matt原版**。

## 2. 输入（必须从现有资料提取，不能猜模块数）

- 递归读取 `docs/input/` 下需求、工程、环境、对接及新增类别的全部相关资料；尤其是**已确认需求基线的项目PRD、模块PRD、角色×核心场景和现有页面/菜单映射**，已有映射直接继承，不重新扫描生成一份。
- `docs/output/01-项目基线/项目基线.md`：技术、性能、资源、数据留存等全局约束。
- `docs/output/02-整体架构/整体架构设计.md`：已审定组件/交互职责、身份/状态Owner及系统边界。
- `docs/output/03-数据库总体/数据库总体设计.md`：已审定数据域与数据Owner、存储/分库策略。
- 实际存在的 `code/deploy/single-node-docker/初次部署配置-<环境名称>.md` 与 `部署结果README-<环境名称>.md`：逐环境核对授权、执行结果与受阻条件；仅有配置不能宣称已经部署。
- `code/` 已存在的实际前后端/Agent/第三方工程：仅定位可复用页面、组件、API与代码模块，不修改代码，也不审查现有框架的质量。

## 3. 拆分流程与判定依据（项目模块级，不发布开发Ticket）

### 3.0 固定拆分判据与优先级

**主判据是业务职责与核心业务对象的完整生命周期**，角色×核心场景用于发现候选及验证覆盖；架构和数据Owner用于校验；依赖用于确定实施关系，**不能反过来凭依赖数量或实施顺序决定模块数量**。

| 顺序 | 依据 | 在本阶段的作用 |
|---|---|---|
| 1 | 角色×核心业务场景 | 从已确认PRD发现业务能力，确保一个完整业务结果可被观察和验收 |
| 2 | 业务职责边界 | 判断能力是否围绕同一业务目标、规则和责任聚合 |
| 3 | 核心业务对象及状态生命周期 | 判断由谁负责创建、变化、终结与追溯，明确权威Owner |
| 4 | 已批准整体架构与数据库总体 | 校验组件、数据域、状态Owner与现有代码复用，不借模块划分重画架构 |
| 5 | 模块依赖关系 | 确定强阻塞、契约依赖和外部阻塞，得出DAG及可实施候选 |

不以单个菜单、页面、数据库表、Controller、代码目录、前后端技术层或单张Ticket直接命名一个业务模块。业务模块边界**不等于**独立服务、Worker或部署单元边界。

### 3.1 从场景发现候选业务能力

逐项读取PRD中的**角色×核心业务场景**，记录业务入口（使用已有原型页面）、触发动作、核心业务对象、状态变化、涉及组件和可观察的业务结果；同时识别权限拒绝、校验失败、驳回、重试等实际有依据的重要分支。不能把“有一个菜单/CRUD页面”视为已经得到可验收的业务能力。

在场景映射表中记录PRD或原型来源，提出**候选归属**，尚不预设模块数量。该阶段只是识别业务能力，不生成实现Ticket，也不因跨前后端、消息队列或数据库就拆成多个模块。

### 3.2 按职责与生命周期聚合、拆分并确定Owner

对每组候选场景，按以下顺序判定：

1. **业务目标与职责**：是否共同完成一个主要业务结果，适合由同一业务责任方维护？是则优先合并；目标和职责明显独立则考虑拆分。
2. **核心对象与生命周期**：是否围绕相同核心业务对象及紧密关联的状态流转（创建、执行、审批、关闭、归档等）？紧密关联优先合并；对象、状态权威及变化规则独立且边界清晰才考虑拆分。
3. **业务规则与独立验收**：合并是否造成职责过杂、规则频繁相互牵制？拆开后能否分别产生真实可验收的业务结果？仅因各自能编码或有页面，不构成拆分理由。
4. **跨模块协作与数据Owner**：对每个可写业务对象和关键状态只能指定一个权威Owner；其他模块只能通过已批准的契约协作，不能各自维护第二套权威状态。每项跨模块场景指定唯一主责模块及协作模块。

每次拆/合必须写出**所依据的场景、对象/状态、职责边界、独立验收结果和决策理由**；有争议时保留候选并交审核，不用主观数量目标替代判断。

每个正式候选模块须明确：模块ID与名称、做什么与不做什么、核心对象及状态Owner、主要角色×场景、现有原型/页面/代码复用点、已定架构组件和数据域、可验收业务结果。一个模块可以跨多个页面和组件，一个页面也可以消费多个模块；**模块只定义业务归属，不擅自新增独立系统、数据库或部署服务**。

### 3.3 按 Matt Blocking edges 建立模块级依赖DAG

为每个模块定义：

- **强阻塞（blocked by）**：下游核心场景必须依赖上游已经交付的真实能力或数据；写明上游模块ID、必须先交付什么、原因及解除条件。仅因建议先开发上游不构成强阻塞。
- **契约依赖**：约定稳定接口、模型和测试替身即可并行开发；明确依赖的具体契约以及何时必须完成真实集成验收。
- **环境/第三方阻塞**：需要账号、真实设备、授权或测试环境；和模块DAG依赖分开说明。
- **无依赖**：可以从本轮选择阶段开始考虑。

给出模块依赖表和 Mermaid DAG；检测循环依赖，将公共Owner/共享契约拆清而不是偷偷删除边。区分“可以开发”与“可以真实验收”，模拟数据不能当作第三方验收完成。

### 3.4 Quiz：项目经理与技术总监审核模块粒度

**像Matt原版to-tickets一样用可理解的列表向用户提问，但提问对象是模块不是Ticket。** 每个模块展示：

`模块名称 | 主要职责与非职责 | 核心对象/状态Owner | 角色×场景与可验收结果 | 拆/合依据 | blocked by与契约依赖`

至少确认：模块是否过粗/过细；合并是否共享同一业务目标与生命周期；拆开后能否分别验收；是否有两个模块同时修改同一权威状态；强依赖是否真实阻塞；PRD是否遗漏、重复或多出了无依据功能；是否擅自新增独立系统。项目经理批准业务范围；技术总监批准系统组件/数据责任和依赖。未确认前只能提交候选清单，不能把草案称为已审定模块池。

### 3.5 反向校验全覆盖与对下游的交付契约

按需求基线逐项核对每个核心场景有且仅有**一个主责模块**（可有多个协作模块），检查入口、业务结果、异常分支与已有原型是否覆盖；漏项做“补”，无依据或重复功能做“删”，Owner/页面/依赖冲突做“改”，保留PRD及原型证据和决策理由。若拆分时发现需求本身有歧义，只记录待澄清项，不能擅自修改已确认PRD。总体组件/通信如需变更，返回S04架构复审；数据域如需变更，返回S05数据库总体设计复审。

**在S07结束后，只有模块池与模块依赖，尚无全项目可执行Tickets。** S09选择真实就绪任务、校验依赖并完成模块详细设计，S10确认本模块Spec，**S11调用未修改的Matt原版`to-tickets`并向已配置Tracker发布单上下文纵向Tickets**。这两个层级分别存储，避免全局模块列表被实现Ticket淹没。

- `docs/output/05-模块拆分/模块依赖关系.md`：模块级DAG、强阻塞/契约依赖/第三方受阻、可优先实施的模块。
- `docs/output/05-模块拆分/模块拆分审核.md`：逐模块拆/合证据、粒度及依赖人工确认、项目经理与技术总监审核、补删改决定和未决冲突。
