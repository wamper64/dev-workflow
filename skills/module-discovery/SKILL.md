# 项目模块拆分

## 前提和输入

递归读取 `docs/input/` 全部与业务/工程相关的已确认资料（已有页面映射不要重做）、`docs/output/01-项目基线/`、`docs/output/02-整体架构/`、`docs/output/03-数据库总体/`、`docs/output/04-开发环境/`。观察 `code/` 原型路由和 `code/` 业务扩展点时只核对归属，不做代码质量审查。

## 业务分组

1. **从能力到模块**：先读取PRD中系统主流程、核心业务场景、角色以及页面清单；定义边界稳定、可独立测试与验收的一组业务能力。一个模块可以覆盖多个页面；一个跨业务流程页面可以调用多个模块。
2. **所有权分析**：按总体数据域、业务状态主责、审批/版本责任和权限边界划分。业务对象由一个模块作权威修改；可复用查询服务不自动变成独立服务。
3. **依赖图**：保持已批准整体架构的组件和交互不变，识别模块需要的前置项目ID、字典版本、模板、计算单、人工确认参数与角色权限，区分“必须先交付的模块”和“预先约定接口即可并行”的依赖。
4. **映射既有工程**：为各模块注明使用现有`code/`页面或组件、在已有后端现有哪个业务包/模块扩展；禁止输出“建议重建一个新的Vue前端”。
5. **业务覆盖校验**：反向从PRD逐个场景查其业务模块归属，重点核对项目实际的登录/权限（如有）、核心业务主链、人工确认/审批（如有）、输出归档、审计。对“遗漏、重复、互相矛盾”执行补、删、改；不为了凑数量产生空模块。
6. **人工评审**：项目经理确认业务完整性与模块名称；技术总监确认数据域和依赖图的一致性。未通过继续调整；不自动为全项目模块同时生成Spec；发现必须改变全局组件/通信的真实新事实，则反馈给architecture-baseline重审。

## 输出

- `docs/output/05-模块拆分/项目模块清单.md`
- `docs/output/05-模块拆分/模块依赖关系.md`
- `docs/output/05-模块拆分/模块拆分审核.md`

按 [验收清单](references/module-gate.md)、[模块清单模板](assets/module-map-template.md)生成。模块拆分是可审核决策，不是固定13模块的合同承诺。

## 业务归属和依赖图的快速读法

```mermaid
flowchart LR
  A[项目PRD场景] --> B[已有原型页面]
  B --> C[操作及业务状态的权威Owner]
  C --> D[模块清单]
  D --> E[依赖DAG]
  E --> F[项目经理与技术总监审核]
```

按 `场景ID | 角色 | 页面/动作 | 模块Owner | 前置依赖 | 已覆盖/遗漏/重叠` 建立逆向追踪表；一条场景可以跨模块，但状态的最终修改责任只能有一个。构造依赖DAG时区分**强依赖（必须实际完成）**与**契约依赖（接口冻结即可并行）**。检测循环依赖时拆开共用对象或明确服务契约，不能偷偷删边。在 `模块拆分审核.md` 对遗漏项做“补”、重复功能做“删”、归属冲突做“改”，记录原因。项目模块数量不固定。
