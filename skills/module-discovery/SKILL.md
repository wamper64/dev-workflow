# 全项目模块识别与划分（基于 Matt Tickets 改造）

## 1. 目标与粒度边界

把已确认的需求基线转化为**整个项目的可分批交付业务模块池**，确定模块边界、角色×核心业务场景、既有页面、系统组件/数据Owner归属以及前置依赖，供下一步选择本轮模块。

本Skill**学习并改造**Matt `to-tickets` 的三个关键机制：

1. **Tracer bullet / 纵向交付**：每个模块至少有一条贯穿实际业务使用路径的可验收场景，不把全部前端、全部后端、全部数据库分别拆成独立业务模块。
2. **Blocking edges / 阻塞依赖**：显式列出什么必须先完成、什么只需接口契约确认就能并行；不以“建议先做”冒充强依赖。
3. **Quiz / 人工校准粒度**：向项目经理与技术总监展示模块名称、实际交付、前置依赖，逐项确认过大/过小、阻塞边是否必要、应该合并或拆开哪些模块。

**与Matt原版的区别必须保留**：原版 `to-tickets` 面向已经确定的计划/Spec产出**适合单个新上下文完成、可发布到Issue Tracker的开发Tickets**。项目模块往往包含多轮设计与多个Tickets，不能伪装成单个可执行Ticket。因此**S07不调用原版发布全项目开发Tickets**，而是在模块级运用同样的可交付与依赖思想；正式单任务Tickets由S11在本轮模块Spec确定后**完整调用Matt原版**。

## 2. 输入（必须从现有资料提取，不能猜模块数）

- 递归读取 `docs/input/` 下需求、工程、环境、对接及新增类别的全部相关资料；尤其是**已确认需求基线的项目PRD、模块PRD、角色×核心场景和现有页面/菜单映射**，已有映射直接继承，不重新扫描生成一份。
- `docs/output/01-项目基线/项目基线.md`：技术、性能、资源、数据留存等全局约束。
- `docs/output/02-整体架构/整体架构设计.md`：已审定组件/交互职责、身份/状态Owner及系统边界。
- `docs/output/03-数据库总体/数据库总体设计.md`：已审定数据域与数据Owner、存储/分库策略。
- `docs/output/04-开发环境/部署步骤与执行记录.md`：真实可用与受阻的开发前置条件。
- `code/` 已存在的实际前后端/Agent/第三方工程：仅定位可复用页面、组件、API与代码模块，不修改代码，也不审查现有框架的质量。
- 如已有 `GLOSSARY.md` 与 `docs/adr/`，继承名称和已确认决定。

## 3. 步骤（项目模块级，不发布开发Ticket）

### 3.1 建立业务交付切片候选

从真实需求基线的每个**角色×核心业务场景**反向识别一条业务可观察路径：操作者从哪里进入、做什么、读写哪类状态/数据、调用哪些已审定组件/接口、完成后能看到什么结果。按 `references/module-gate.md` 检查正常、权限拒绝、驳回/重试等重要分支是否存在，避免只列CRUD页面。

候选是“可被验收的业务能力”，**不是已可由Agent领取的Ticket**。真实PRD里属于同一业务Owner与状态生命周期、且通常应一起交付的切片可聚合到一个模块；不要先按菜单数量、数据库表或代码目录决定模块数量。

### 3.2 聚合业务模块并守住整体骨架

依据已批准的**组件职责、数据域/权威Owner和业务状态责任**聚合候选切片。每个模块必须明确：唯一模块标识、业务边界、主要场景与页面、依托的组件/数据域、既有代码复用点、可验收的交付结果、不属于本模块的内容。

同一个模块可以跨多个页面；同一个页面也可能调用多个模块，但每个可写业务对象/状态只能有明确的权威Owner。模块数量没有预设目标；若某项横跨多模块则明确谁主责、谁只消费。

### 3.3 按 Matt Blocking edges 建立模块级依赖DAG

为每个模块定义：

- **强阻塞（blocked by）**：必须已有上游已交付行为/数据，未满足无法独立完成核心场景。
- **契约依赖**：只需双方约定稳定接口/假数据边界就可并行实现，真实集成验收仍依赖实际接口。
- **环境/第三方阻塞**：需要账号、真实设备、授权或测试环境；和模块DAG依赖分开说明。
- **无依赖**：可以从本轮选择阶段开始考虑。

给出模块依赖表和 Mermaid DAG；检测循环依赖，将公共Owner/共享契约拆清而不是偷偷删除边。区分“可以开发”与“可以真实验收”，模拟数据不能当作第三方验收完成。

### 3.4 Quiz：项目经理与技术总监审核模块粒度

**像Matt原版to-tickets一样用可理解的列表向用户提问，但提问对象是模块不是Ticket。** 每个模块展示：

`模块名称 | 交付什么实际业务结果 | 主要角色×场景 | blocked by | 契约依赖 | 在既有架构中的Owner`

至少确认：模块是否过粗/过细、哪些依赖是真正阻塞、是否应该拆分/合并、PRD是否有遗漏与重复、是否新增了无依据的独立系统。项目经理批准业务范围；技术总监批准系统组件/数据责任和依赖。未确认前只能提交候选清单，不能把草案称为已审定模块池。

### 3.5 反向校验全覆盖与对下游的交付契约

按需求基线逐项核对每个核心场景能找到**唯一主责模块**和相关协作模块；漏项做“补”，无依据或重复功能做“删”，Owner/页面/依赖冲突做“改”，记录理由。总体组件/通信如需变更，返回S04架构复审；数据域如需变更，返回S05数据库总体设计复审。

**在S07结束后，只有模块池与模块依赖，尚无全项目可执行Tickets。** S08选择真实就绪模块，S09补当前模块详细设计，S10确认本模块Spec，**S11调用未修改的Matt原版`to-tickets`并向已配置Tracker发布单上下文纵向Tickets**。这两个层级分别存储，避免全局模块列表被实现Ticket淹没。

## 4. 正式输出

- `docs/output/05-模块拆分/项目模块清单.md`：业务模块、角色×场景、已有原型/代码、组件/数据Owner、可验收结果。
- `docs/output/05-模块拆分/模块依赖关系.md`：模块级DAG、强阻塞/契约依赖/第三方受阻、可优先实施的模块。
- `docs/output/05-模块拆分/模块拆分审核.md`：项目经理与技术总监真实审核、补删改决定和未决冲突。

使用 [模块业务边界与依赖审核](references/module-gate.md) 和 [模块清单与DAG模板](assets/module-map-template.md)。

**禁止事项**：不预生成全部模块Spec、不发布全项目开发Tickets、不让模块直接等于单张Ticket、不为分模块而新造顶层Worker/服务、不改变已批准PRD或原型的视觉样式。
