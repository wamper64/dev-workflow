# 自动化覆盖 → 人工用例的判定规则

## 1. 必须取真实证据

| 决策 | 必需依据 | 后续动作 |
|---|---|---|
| 已自动验证 | 真实执行命令、通过日志/截图、测试数据与环境、可追溯用例 | 记录证据，不重复编一条人工用例 |
| 必须人工验证 | AI无法可靠判断视觉/交互/操作体验、真实现场、角色流程或交付结果 | 产生待执行人工用例 |
| 当前受阻 | 无真实设备、第三方账号/环境、测试数据、浏览器工具或实际权限 | 写明阻塞与必要人工条件，不能算通过 |
| 无人工覆盖缺口 | 已覆盖角色×场景有证据，且无人工能力依赖 | 写明筛选结论与证据，不为格式造用例 |

## 2. 从需求基线选用例

- [ ] 每个核心角色×场景均明确“自动已覆盖/人工待测/受阻/不适用”及依据。
- [ ] 对现有前端原型，截图差异只能在同状态/同视口且保留基线的前提下作证；缺工具则转人工测试。
- [ ] 多用户审批、驳回重提、业务状态和授权，需要按真实角色和可观察结果验证。
- [ ] 真实第三方/设备不可用时，不以Mock测试宣称业务已验收。
- [ ] 本步骤不执行人工测试，不填写通过、测试人和真实结果；不调用新的review/TDD。
- [ ] Ticket未完成/未review通过时，明示实现阻塞，不能把人工测试单生成视为研发完成。

每条待人工测试用例具有可执行步骤和**可观察结果**，不得写“检查是否正确”这种无法判定的预期。


## 本可自动测试但没有执行的缺口

这类缺口不得直接交给人工凑数，先返回Matt原版实现步骤补测试；环境无法执行时明确阻塞和可复现条件。任务完成后人测结果必须保留失败与原用例复测历史；由人工签收后再更新项目状态，不交给retro更新。
