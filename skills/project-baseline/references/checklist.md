# 工程基线内容检查清单（仅供 Skill 内部使用）

| 领域 | 核查项 |
|---|---|
| 业务取舍 | 什么业务错误最不可接受；哪些原则能够否决架构方案 |
| 范围 | 自建、复用与第三方责任边界；明确不做 |
| 技术 | 明确裁定的语言、版本、已有框架、可替换范围 |
| 现有代码 | 现状只有被明确要求沿用、实际不可变或经裁定，才可写为硬约束 |
| 环境 | 目标CPU、内存可用量、磁盘类型与余量、系统、网络、部署方式、是否能扩容 |
| 并发 | 在线人数、活跃人数、请求并发、长任务并发分别表达 |
| 数据 | 权威来源、修订追溯、保留起点、备份范围 |
| 集成 | 第三方协议、授权、超时、重试、幂等和故障责任 |
| 质量 | 响应口径、数据量与混合负载、持续时间、恢复范围与限时 |
| 运行资源 | 内存、连接、句柄、线程、队列、日志及临时文件的有界使用、耗尽降级 |
| 交付 | 离线部署、数据库升级兼容、备份恢复、回滚 |

## 必要判断

- PRD提到50个在线用户：不等于50个请求并发。
- `code/guiwu_ruoyi` 使用 Java8，不代表PRD明确新项目用Java17时必须保留Java8。
- 原型 `code/fld` 明确要延用外观，应写为不可大改的硬约束。
- 目标服务器没有CPU/内存/磁盘：给出有依据的推荐并提问，不假定8C16G。
- Redis在代码里被声明但没有约定使用：不能自动升级为项目必需技术。
- TDD、Tickets、代码评审属于研发执行规则，不进入工程基线正文。
- 输出文档不写资料盘点、读文件过程、阻塞矩阵或状态清单。

## 最终审查

1. 有没有可裁决设计选择的第一性原则？
2. 容量、权限、保留与故障范围是否相互一致？
3. 是否将无依据数值、其他项目默认参数误写成当前项目事实？
4. 是否把已确认PRD重写成另一份业务功能详单？
5. 章节是否连续编号，表格是否一行表达一项约束？
