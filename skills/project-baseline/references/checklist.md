# 项目基线生成覆盖检查

每项必须有**数值+单位+适用口径**或在会话中显式追问并说明无法定稿；“有标题”不代表通过。

- [ ] 第一性原则：从报价业务错误代价推导可否决方案的规则
- [ ] 技术栈：前端框架、构建、组件、后端语言/框架版本、DB、中间件按需版本
- [ ] 服务器：CPU架构和核数、内存总/可用、磁盘总/可用/类型、OS、部署/网络/扩容
- [ ] CPU：OS、DB、API、worker、缓存/网关各预算与总核数闭合
- [ ] 内存：各运行单元GiB绝对上限+安全余量合计与目标机闭合
- [ ] 磁盘：系统、数据库、附件、日志、临时、备份、空余GB分配闭合
- [ ] 并发：用户总量、在线、HTTP请求、长任务并发和排队容量明确区分
- [ ] 数据保留：各类报价/版本/计算单/审批/附件保存N年，起算点兼容，运行日志按月计
- [ ] 性能：主要查询/提交的P95数值、测试数据量、同时请求、测试时长与边界
- [ ] 稳定性：进程RSS、数据库连接、线程、文件句柄、日志等绝对上限、浸泡时长、回归阈值
- [ ] RPO/RTO：数据、附件和系统配置所需备份/恢复范围
- [ ] 整体设计否决力：基线能限制未经过审查的技术改造和资源过量分配

## 常见失败

“有8核16GB但未分资源预算”“数据需长期保存”“响应应尽可能快”“并发50人（未区分在线/HTTP请求）”“定期备份（无RPO/RTO）”均不得视为已完成工程基线。

缺项要主动提出**具体推荐值、理由、适用前提及代价**，每轮最多3问；用户未裁定的数据不写入最终基线。
