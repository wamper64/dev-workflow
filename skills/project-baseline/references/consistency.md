# 约束一致性检查

生成前核对明确要求、推导、建议与最终裁定是否一致。

| 对象 | 禁止隐式修改 |
|---|---|
| 技术协议 | MQTT改HTTP、推送改轮询、已定登录方式改SSO |
| 时间和期限 | 72小时改7天、24个月改5年、时间起算改变 |
| 性能 | P95改全部请求、服务端耗时改端到端耗时 |
| 并发 | 在线人数等于请求并发、任务执行并发等于受理容量 |
| 对接 | 第三方未知能力伪装为已支持或已上线 |
| 责任 | 客户服务器目标配置伪装为现有资源或第三方承诺 |

## 关键闭合关系

- **保留期**：结果、原始输入、修订依据的保存期限兼容；如果不兼容，需用户在保存原始数据/快照/调整追溯范围间裁决。
- **容量**：业务数据、索引、日志、备份、临时文件和进程内存必须能够在目标服务器资源预算内闭合；不能凭记录数声称磁盘充足。
- **长任务**：受理、排队、执行和完成的定义一致；排队无界无法保证有限完成时限。
- **性能测试**：保留环境、负载、数据集、统计口径、场景比例及持续时长。
- **数据修订**：历史重算不能静默覆盖已确认版本，具体结果根据本项目PRD裁定。
- **恢复**：恢复目标是否涵盖业务数据、应用配置、身份与权限、部署介质和第三方可用性；RPO基于成功可恢复点，而不是备份计划间隔。

需改变已有明确目标时在会话提出推荐并得到确认；不得为了让文档“更先进”而擅自提升约束。
