# 工程约束一致性检查

项目基线只能把已确认需求、客户条件、既有工程以及负责人裁定转为**不可违反的约束**；不得以「完善文档」为理由偷偷改动已有要求。

| 检查对象 | 必须避免的隐式修改 |
|---|---|
| 需求与约束 | 把功能清单、页面/菜单、分期不做事项再次写成一份PRD |
| 约束与设计 | 把可选组件拓扑、数据库表、Kafka/微服务/Worker数变成未经批准的硬约束 |
| 现有代码 | 代码里安装了Redis就强迫生产必须使用；Java8现状就覆盖已明确的Java17目标 |
| 版本/协议 | MQTT改HTTP，已批准的框架版号被示例替换 |
| 时效与数据 | 前一天完整数据冒充实时；缺失数据冒充零；采样时间替换为入库时间 |
| 计量与期限 | 72小时改7天；保留年限、起算点或历史修订界限发生变化 |
| 负载与性能 | 50人在线直接变50并发；P95服务端误写成页面端到端 |
| 异步与审批 | 后台任务排队时长误写为执行时长；有审批就强制采用异步Worker |
| 角色与权限 | AI/第三方越权、现有认证体系无授权即被替换 |
| 测试与恢复 | 把计划值当成实测通过；本机备份当作已有异机可恢复副本 |
| 用户推荐 | 方案建议未经裁定直接进入正式基线 |

## 必须闭合的关系

- **事实来源**：同一约束不同材料不一致，应形成待确认冲突，不自行选较方便的一项。
- **容量**：数据增长、索引附件、保存期限、日志与备份，与已批准服务器上限及安全余量一致。
- **性能**：负载构成、在线与请求并发、数据集、统计口径、测试环境和时间窗口一致。
- **后台任务**：受理、排队、执行、完成、取消、失败和重试的限制不互相矛盾；在项目基线阶段只定不变量和边界，不设计实现。
- **数据与权限**：权威源、只读能力、历史版本、审计要求与对接材料一致。
- **恢复**：数据库、附件、配置等恢复范围和RPO/RTO，与确实存在的备份介质及网络相容。

关键冲突未裁决则前置表标注阻塞并提出方案，不得把正式基线标为已完成。
