# 从需求与工程资料提取「约束」的判定规范

## 核心原则

需求解析可得到的规模、频率、精度、期限、阈值等内容，必须尽量提取为**量化事实/目标**；但不是将所有需求机械地变成基线。只有跨模块或影响工程边界、验收与重大取舍的部分才进入基线。

## 需求、约束和设计的三分法

| 读取到的内容 | 分类 | 如何处理 |
|---|---|---|
| 用户可导出Excel | 需求 | 留在PRD，不添加功能型基线 |
| 已确认每次最多导出10万行，超限须明确拒绝 | 候选约束 | 记录行数、单位、适用场景和依据，确认是否形成跨模块能力边界 |
| 采用异步消息队列导出 | 设计 | 交给架构/模块设计；仅当已批准为硬约束才引用 |
| 前端必须基于既有原型开发且不重做组件体系 | 工程约束 | 写禁止边界和允许修改范围 |
| 本期不做移动App | PRD交付范围 | 不重复；若意味着不采购移动端专项平台，可只写已批准的工程限制 |
| 读取第三方数据库，禁止写入 | 跨系统约束 | 写明确读写边界与验证规则 |
| 要求页面刷新快 | 待澄清目标 | 推荐响应时限、统计口径、负载条件，等待裁定 |

## 候选约束有效性

每条至少具备：**触发条件/适用对象、必须/禁止、可检验结果、来源及确认状态**。可量化条款进一步提供：指标名、值/上下限、单位、统计周期、样本范围、测量边界及适用环境。若缺关键口径，作为待裁定问题而非正式值。

无法合理用数字表达的规则应有**二值验收**（是否访问越权数据、是否重建平行前端、是否在第三方只读库执行写入等），不是为了「量化」虚构数字。

## 提取项目特有基线的检查方向

- **既有资产不可破坏**：前端原型视觉、公共组件、后端已有权限、客户既有数据库/协议兼容。
- **数据有效性**：来源权威、业务时间语义、统计修订、历史结果不可静默覆盖。
- **风险取舍**：自动建议不能成为正式事实、危险指令必须授权确认、失败不能冒充真实成功。
- **环境不可变因素**：本地/内网/单机、禁止公网、固定网络协议、第三方只有前一天完整数据。
- **禁止事项与责任**：禁用未经批准的外部服务、数据库只读、第三方不保证的能力不得写成本系统承诺。
- **全局指标**：用户规模、设备量、年增长量、采样周期、有效期、任务规模、性能、恢复。

**不做判定**：需求「不开发X功能」与工程「禁止Y行为」分开；只有后者进入正式基线。前者最多用于解释适用范围，不把PRD裁剪成另一份需求清单。
