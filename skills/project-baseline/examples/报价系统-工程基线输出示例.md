# 报价系统项目工程基线

本文定义报价系统的第一性原则和工程约束，作为整体架构、数据库总体设计、模块开发、测试和上线交付的共同边界。

## 1. 第一性原则与取舍

| 原则 | 必须保证的结果 | 冲突时优先级与禁止边界 |
|---|---|---|
| 人工确认优先于自动推断 | 需求解析产生的是待核对参数；只有人工确认的参数版本才能进入计算单匹配、成本核定和正式报价 | 为缩短响应时间，不得跳过参数人工确认；AI 推断结果不得冒充客户确认 |
| 报价版本可追溯 | 已提交或已审批的报价能定位到相应的需求参数版本、计算单依据、模板和成本版本 | 新解析、重新匹配或重新核定不得静默改写已确认版本 |
| 权限和审批由后端裁决 | 实际业务状态、领取/审批/驳回与数据访问权限由服务端验证 | 页面隐藏按钮、前端传入角色或 AI 建议不能绕过服务端权限 |
| 真实交付优先于伪成功 | 第三方解析、审批、文件生成失败时展示真实状态与恢复入口 | 不得把模拟返回、超时或未执行操作标记为真实成功 |
| 延用已确定工程资产 | 在已有原型和若依框架上建设后续功能 | 不得另建一套视觉体系或平行的用户/权限后台 |

## 2. 建设范围与责任边界

| 对象 | 范围与责任 |
|---|---|
| 业务系统 | 项目管理、字段词典、历史计算单、需求解析与核对、报价模板、匹配、成本核定、报价审批、输出与归档 |
| 前端 | `code/fld/` 作为实际研发基础；直接接入业务 API，沿用现有路由、组件布局和视觉样式；允许经审核的小范围细节调整 |
| 后端 | `code/guiwu_ruoyi/` 作为实际框架基础；复用其既有认证、角色、菜单等适用能力，在其组织内扩展业务 |
| 第三方或外部计算服务 | 对外部系统负责的计算或解析结果必须记录实际调用状态；未知能力不能当作已支持 |
| 人工参与 | 需求参数确认、审批权限和归档操作按PRD中确定的角色执行；AI 仅提供辅助结果 |

## 3. 技术与部署边界

### 3.1 技术与工程复用

| 范围 | 必须沿用的边界 |
|---|---|
| 前端 | `code/fld/` 的技术栈与组件模式以其实际已选版本为准；不得因为增加AI能力重新搭建SPA或更换UI体系 |
| 后端 | `code/guiwu_ruoyi/` 的框架与通用能力复用；确需调整底层版本必须先做兼容评估并经技术总监确认 |
| 数据库 | 采用项目已裁定的关系型数据库作为事务性业务数据权威存储；分库分表策略由下一阶段数据库总体设计确定 |
| 集成 | 统一服务端鉴权与超时处理；外部接口失败不影响已确认版本的完整性 |
| 部署 | 目标客户环境允许以容器方式部署，应用必须有可独立验证的启动、健康检查及配置管理能力 |

### 3.2 服务器与运行环境

| 项 | 本示例已假设确认的目标条件 |
|---|---|
| 服务器 | 单台 x86_64 虚拟机，8 vCPU |
| 内存 | 16 GiB；运行资源预算须留有系统与恢复余量 |
| 磁盘 | 500 GiB SSD；用于应用、数据库、附件、日志、备份与临时导出，必须为增长预留空间 |
| 系统 | Ubuntu Server 22.04，允许 Docker 容器 |
| 伸缩 | 初始部署以单机可运行、可恢复为原则；增加运行单元或资源须复评容量 |
| 网络 | 外部解析接口按已确认的连通性、认证和出网策略设计；不得假设客户内网能访问未授权的公网服务 |

## 4. 规模、并发与资源边界

### 4.1 业务负载

| 对象 | 规模与口径 |
|---|---|
| 使用者 | 设计目标为 50 人**在线**，不直接等价于 50 个 HTTP 同时执行请求 |
| 长任务 | 单次需求解析或计算任务可持续最多 20 分钟；必须有独立执行状态，不依赖浏览器请求一直保持连接 |
| 排队 | 接收任务、开始执行、完成和失败分别定义；长任务排队不能被统计为已经完成 |
| 用户操作 | 多人操作同一报价项目时，提交/审批动作需具备服务端并发保护，不允许双重完成 |

### 4.2 数据增长

| 对象 | 应纳入容量测算的增长口径 |
|---|---|
| 项目与报价记录 | 新增项目数 × 项目版本数 × 报价修订次数 |
| 需求文件和计算单 | 上传文件量、平均文件大小、生成附件数及版本保留数量 |
| 审批与审计 | 审批层级、操作事件、重提次数及审计保留期限 |

在本示例没有提供具体文件量、历史项目总数和修订分布时，不以推测值推导“500 GiB 足够”。容量设计应按当前环境上限测算并明确可容纳的文件/数据规模。

### 4.3 资源使用边界

| 资源 | 必须遵守的限制 |
|---|---|
| 内存 | 所有运行单元、数据库、缓存与基础服务总预算不得超过单机可用内存，保留系统和异常恢复余量 |
| 连接与线程 | 数据库连接、HTTP 连接与后台线程均有上限；超限要拒绝或排队，不能无限创建 |
| 异步任务 | 长任务并发和等待队列必须受限，取消或失败后资源可释放；不能以增加线程数无限承诺吞吐 |
| 文件与磁盘 | 上传、解压、计算中间文件、导出、日志和备份分别设置大小/留存边界，长期运行不得无界增长 |
| 常驻缓存 | 采用有界容量、失效及回收行为；缓存失效不能破坏事务数据的权威性 |

## 5. 数据一致性、安全和生命周期

### 5.1 跨环节不变量

| 业务场景 | 不变量 |
|---|---|
| 需求再次解析 | 新解析结果只能形成新的待核对参数，不得覆盖旧的人工确认结果 |
| 参数确认 | 正式匹配或成本核算须引用明确的参数版本；版本变化时关联结果必须可追溯 |
| 报价审批 | 服务端按当前待办、领取状态和用户授权执行；同一审批操作重复提交不能产生两次业务完成 |
| 审批驳回与重提 | 驳回后的流程回退及再次审批必须依据当前流程定义；保留原审批历史 |
| 文件输出 | 客户文档只能基于获准输出的报价版本生成；失败任务不得生成“已交付”状态 |

### 5.2 权限

| 范围 | 原则 |
|---|---|
| 账号与角色 | 沿用已有后台可适用的认证授权机制；组织和项目级数据范围在服务端强制执行 |
| 审批 | 操作人是否有权审批、是否为当前任务处理人和流程状态都必须在服务端判断 |
| AI/第三方 | 自动执行服务不能绕过原业务权限；传递给外部的业务参数和文件遵守客户的数据边界 |
| 审计 | 对参数确认、报价版本变更、审批决定与归档操作保留能追溯到用户、时间与业务对象的记录 |

### 5.3 生命周期

报价版本、审批日志与所依赖的计算依据应具有相互兼容的保留期限；归档及删除不得留下无法解释的最终报价。实际保留年限须以项目确认的业务和合规要求为准。

## 6. 质量与恢复底线

### 6.1 可验收行为

| 类别 | 评价标准 |
|---|---|
| 正确性 | 已确认版本与计算和审批关联关系不允许静默错配；重复操作不能产生重复审批结果 |
| 请求 | 常规业务 API 响应目标须按具体负载、数据量、P95等统计口径裁定后应用 |
| 长任务 | 在约定的最大受理与执行条件下，能准确观察排队、执行、失败、取消和完成状态 |
| 稳定性 | 在已确定的长时间持续负载下，内存、连接数、日志与临时文件不存在累积性无界增长 |
| 恢复 | 从数据库、附件与应用配置的有效备份恢复后，应能继续正确识别已确认报价、审批状态和附件 |

### 6.2 验收条件与责任边界

| 检查条件 | 底线 |
|---|---|
| 测试环境 | 与目标服务器资源限制相符，明确数据库、应用及外部依赖是否同机 |
| 业务场景 | 覆盖多用户登录、并发提交、长任务、文件导出、驳回/重提和异常网络 |
| 统计口径 | 在线人数、同时请求数、后台任务并发及连续运行时长分别报告 |
| 判定规则 | 任何“完成、通过、已交付”状态都需有真实后台记录与可追溯结果 |

## 7. 运行与交付边界

| 主题 | 交付约束 |
|---|---|
| 安装升级 | 提供支持目标客户环境的部署/升级流程、配置样例和版本化数据库变更能力 |
| 数据安全 | 数据库与附件有备份、恢复和升级前保护方案；回滚不能隐式丢弃已完成审批与已确认报价 |
| 运维 | 应能通过日志和健康状态定位接口故障、长任务异常、磁盘压力和资源耗尽 |
| 交付物 | 前后端可部署版本、配置说明、数据库变更、业务验收和部署交接材料须与发布版本对应 |

## 8. 基线变更边界

技术栈、前端原型改造范围、客户服务器容量、长任务量级、数据保留年限、业务版本与审批权限原则发生变化时，必须重新审核受影响的总体架构、数据库总体和模块设计；不得通过局部代码改动静默改变本基线。
