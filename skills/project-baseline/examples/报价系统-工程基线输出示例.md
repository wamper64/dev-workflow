# 报价系统工程基线——完整运行效果示例

> **演示，不是报价项目的真实已确认基线。** 这份文档模拟 `project-baseline` 在获得完整输入和用户裁定后应交付的形态。示例技术版本、服务器规格、并发指标、保存年限、资源配额和SLA数值均为**假设已经确认的演示值**；不能直接套用到真实客户。真实执行时应读取 `docs/input/`，对缺口给出数值推荐并取得明确确认。

## 演示用的模拟确认条件（不属于交付的基线正文）

- 客户模拟批准：单机 x86_64、8 vCPU、16 GiB、500 GB SSD、Ubuntu 22.04、Docker Compose，另有可实际恢复的独立离机备份存储；不允许默认公网出站。
- 开发模拟裁定：Vue 3.5、Vite 6、Element Plus 2.9、Java 8、Spring Boot 2.7、RuoYi-Vue 3.8.8、MySQL 8.0、Redis 7.2、Nginx 1.24。**这些只是演示版本，不代表已核实 code/fld 与 code/guiwu_ruoyi 的真实版本。**
- 业务模拟裁定：50人在线、12个同时执行的常规HTTP请求、2个后台长任务并行、任务排队最多10个；全部核心业务数据从项目归档起保存5年，运行日志保存180天。
- 性能模拟裁定：数据库15,000个报价项目、附件约120GB场景下的查询、提交指标按本文6.1；离机每日增量/周期完整备份，RPO≤24小时，RTO≤8小时。
- 数据增长模拟假设：DB初始20GB、每年新增12GB；附件初始10GB、每年新增22GB；5年计划容量分别约80GB、120GB。

# 报价系统项目工程基线

本文定义项目的第一性原则和工程约束，作为系统整体架构、数据库总体、模块详细设计、测试及交付共同遵守的边界。

## 1. 第一性原则与取舍

| 原则 | 必须保障的结果 | 冲突时的禁止边界 |
|---|---|---|
| 人工确认优先 | 解析生成的需求参数只有在授权用户人工确认后才能用于正式匹配和报价 | 不得为缩短耗时而跳过人工确认 |
| 版本与依据可追溯 | 正式报价必须能关联参数版本、计算单依据、成本核定及审批记录 | 新解析与重新核定不得静默改写已审批报价版本 |
| 服务端控制权限 | 读取/修改/审批均按后端身份及数据权限判定 | UI隐藏、AI建议和模拟请求不能替代服务端鉴权 |
| 真实结果优先 | 第三方或长任务失败须真实呈现失败状态并支持恢复 | 不得将模拟或超时结果显示为真实成功 |
| 复用已有工程 | 现有前端原型和若依框架继续作为开发基础 | 不得另建一套页面视觉风格或独立管理框架 |

## 2. 建设范围与责任边界

| 对象 | 责任 | 全局边界 |
|---|---|---|
| 业务系统 | 自研 | 项目、字典、模板、解析与核对、历史计算单、匹配、成本、报价审批、归档等 |
| 前端 | 基于现有代码扩展 | `code/fld/` 的路由、组件、布局和样式沿用，仅允许经过确认的小范围样式调整 |
| 后端 | 基于现有框架扩展 | `code/guiwu_ruoyi/` 内继续实现业务，复用适用的身份、角色、菜单和审计 |
| 外部解析/计算 | 实际对接的第三方负责其服务结果 | 未核实的第三方接口不能写成正式已交付能力 |
| 参数确认与审批 | 已授权的业务用户负责 | AI提供候选，不能代替人工完成要求人工确认的审批或参数核对 |

## 3. 技术与部署约束

### 3.1 已统一的技术栈

| 领域 | 模拟已经确认的技术与版本 | 使用和升级边界 |
|---|---|---|
| 前端框架 | Vue 3.5 | 在现有 `code/fld/` 上扩展，不另建SPA |
| 构建与UI | Vite 6、Element Plus 2.9 | 沿用已完成原型的设计体系及通用组件 |
| 后端语言 | Java 8 | 与现有若依后端依赖保持兼容，升级需整体审核 |
| 后端框架 | Spring Boot 2.7、RuoYi-Vue 3.8.8 | 延用RuoYi鉴权、菜单及业务扩展方式 |
| 数据库 | MySQL 8.0 | 承载报价业务权威数据，使用版本化数据库迁移 |
| 缓存 | Redis 7.2 | 用于经架构裁定的缓存、限流及状态需求，不替代业务权威数据 |
| 反向代理 | Nginx 1.24 | TLS与请求转发在统一代理层处理 |
| 容器 | Docker Engine 24、Compose 2.24 | 使用单机容器部署，禁止依赖未获允许的外网下载 |
| 额外服务 | 本演示没有强制RabbitMQ或Flowable版本 | 后续实际需求若必须引入，先变更项目基线再设计 |

### 3.2 目标服务器和部署环境

| 项目 | 本示例的已裁定边界 |
|---|---|
| CPU | x86_64、8 vCPU |
| 内存 | 16 GiB（包含操作系统及全部运行单元） |
| 磁盘 | 单块500 GB SSD（预算包含操作系统、镜像、数据库、附件、临时文件和本地备份暂存） |
| 系统 | Ubuntu Server 22.04 LTS |
| 部署形态 | 客户内网单机Docker Compose，按第4章限制各进程资源 |
| 网络 | 不默认具备公网出站；内网业务入口由Nginx代理 |
| 扩容 | 初期不能依靠自动水平扩容承诺性能；改变服务器规格须复评资源预算 |
| 备份 | 另外具备**已经确认且可恢复的独立离机备份存储**；单块500GB业务盘不是完整离机备份 |

## 4. 规模、并发与容量

### 4.1 业务负载上限

| 场景 | 目标数值 | 计量口径 |
|---|---|---|
| 在线业务用户 | 50人 | 保持登录会话的用户数，不等同HTTP同时执行数 |
| 同时执行的常规请求 | 12个 | 服务端同时处理的常规业务HTTP请求，不包含后台任务本体 |
| 后台长任务并发 | 2个 | 真正处于执行状态的解析/计算任务 |
| 等待队列上限 | 10个 | 排队任务尚未开始执行，满额后拒绝新任务并提示 |
| 长任务时限 | 单任务执行≤20分钟 | 自真正开始执行到终结状态，不包含排队等待；端到端等待另行显示 |

### 4.2 数据量和增长（模拟规划量）

| 对象 | 基础量及增长口径 | 五年数据量目标 |
|---|---|---|
| 业务数据库 | 当前20GB + 每年新增12GB，含规划的索引与业务审计量 | 约80GB，预算110GB |
| 原始附件及输出文件 | 当前10GB + 每年新增22GB | 约120GB，预算150GB |
| 报价项目数量 | 每年约3,000个，每年增长不含额外版本膨胀 | 五年新增约15,000个项目 |
| 运行日志 | 最长180天，同时按照总量上限轮转 | 常驻占用≤20GB |

### 4.3 CPU预算（合计8 vCPU）

| 运行单元 | 预算vCPU | 说明 |
|---|---:|---|
| OS、Docker与代理 | 1 | 单机系统进程及入口 |
| MySQL | 2 | 查询与事务 |
| 业务API | 2 | 若依业务服务 |
| 长任务worker | 2 | 解析/匹配/导出任务 |
| Redis和辅助服务 | 1 | 缓存及必要基础服务 |
| **合计** | **8** | **与目标总核数闭合；预算并非已实测可达吞吐** |

### 4.4 内存预算（合计16 GiB）

| 运行单元 | GiB上限/预留 | 口径 |
|---|---:|---|
| OS及容器开销 | 3 | 操作系统、Docker和文件缓存预算 |
| MySQL | 4 | 实例容器内存总量上限 |
| 业务API | 3 | 进程RSS上限，JVM堆须留足非堆空间 |
| 长任务worker | 2 | 任务进程RSS总量上限 |
| Redis | 1 | 实例和缓存使用边界 |
| Nginx及代理辅助进程 | 0.5 | 网关及入口服务 |
| 安全余量 | 2.5 | 留给波动和正常操作系统运行 |
| **合计** | **16** | **不得配置使所有单元峰值超过16GiB** |

### 4.5 磁盘预算（合计500GB）

| 占用 | GB预算 | 清理或增长规则 |
|---|---:|---|
| 操作系统和容器镜像 | 60 | 清理旧镜像与包缓存 |
| MySQL业务数据库和索引 | 110 | 对照每年12GB增长预测复核 |
| 上传附件和报价输出 | 150 | 五年约120GB计划容量 |
| 应用日志 | 20 | 轮转，总占用上限20GB |
| 临时导出/上传与计算文件 | 30 | 任务完成或失败后清理 |
| 本地备份暂存 | 50 | 仅作离机备份中转/临时增量，不承诺容纳全量恢复介质 |
| 必须保留的空闲容量 | 80 | 磁盘剩余空间保护线 |
| **合计** | **500** | **完整备份必须落到已确认的独立离机存储** |

### 4.6 运行期资源底线

| 资源 | 已裁定的绝对上限与行为 |
|---|---|
| API进程RSS | 稳态≤3GiB；超限告警及排查，不能无限追加缓存 |
| 长任务worker RSS | 总体≤2GiB；2任务同时执行时不得内存无限累积 |
| MySQL数据库连接 | 实例内最大业务连接80个；任务与请求完成后必须释放 |
| API线程 | 业务线程总数≤120，不能每次请求无限新建线程 |
| 文件句柄 | 业务API进程打开句柄数≤4096 |
| 等待队列 | ≤10个，超过后拒绝并记录原因 |
| 运行日志 | ≤20GB，按大小及时间轮转 |
| 临时文件 | ≤30GB；完成、取消和失败后按规则清理 |

## 5. 数据、安全与生命周期

### 5.1 数据一致性

| 业务场景 | 必须保证的结果 |
|---|---|
| 重新解析需求 | 新解析结果为候选版本，不能覆盖人工确认版本 |
| 历史计算单匹配 | 匹配结果记录所引用的参数版本与计算单依据 |
| 多级报价审批 | 当前任务处理人、流程状态和数据权限由后端校验 |
| 审批驳回重提 | 原审批动作和关联报价版本必须保留追溯链 |
| 客户报价输出 | 只对允许交付的已确定报价版本生成文件，失败不能标成成功 |

### 5.2 各类数据保存年限

| 数据对象 | 保存时长 | 起算时点 | 清理与追溯边界 |
|---|---|---|---|
| 项目、报价和确认报价版本 | **5年** | 项目成交归档或正式终止日 | 在保留期内不可物理删除被引用版本 |
| 已确认需求参数与修订历史 | **5年** | 所属项目归档或终止日 | 随项目报价版本保持可追溯 |
| 历史计算单和成本核定依据 | **5年** | 所属项目归档或终止日 | 若仍被其他在保留期内报价引用，延期至最后引用关系到期 |
| 业务审批、驳回和审计历史 | **5年** | 所属项目归档或终止日 | 保存操作人、时间、业务版本及审批结果 |
| 上传的原始需求资料、生成的客户输出 | **5年** | 所属项目归档或终止日 | 与参数及报价版本同一追溯期限 |
| 应用普通运行日志（不含业务审计） | **180天** | 日志产生时刻 | 到期清理，同时遵守20GB空间上限 |
| 运行备份中转文件 | **7天以内** | 备份中转文件生成时 | 仅限本机临时副本；离机完整备份按独立恢复策略 |

### 5.3 身份和数据权限

| 对象 | 约束 |
|---|---|
| 业务访问 | 后端根据当前登录身份、角色与可见项目范围授权，不能仅靠前端隐藏 |
| 报价审批 | 审批角色、领取状态与流程任务归属必须由后端核验 |
| 外部调用 | 第三方和AI调用按已批准业务权限与数据最小必要范围访问 |
| 业务审计 | 审批记录与报价版本关联，保留至5年链路到期 |

## 6. 性能、长期稳定性与恢复

### 6.1 量化性能目标（演示SLA）

| 场景 | 目标 | 适用口径 |
|---|---|---|
| 常规报价项目列表 | **P95≤2.0秒** | 服务端接收请求至完整响应结束，不含浏览器渲染 |
| 项目详情查询 | **P95≤1.5秒** | 同上 |
| 报价编制/保存提交 | **P95≤3.0秒** | 服务端完成事务并返回确认结果 |
| 长任务受理返回 | **P95≤1.5秒** | 接受请求返回任务ID，不包含后台执行耗时 |
| 长任务执行 | **单任务≤20分钟** | 不含排队，超时须进入明确异常状态 |
| 常规业务请求失败率 | **≤0.5%** | 在约定负载下计算非用户参数错误引发的服务端失败 |

### 6.2 测试条件和计时口径

| 维度 | 约定 |
|---|---|
| 测试服务器 | 第3.2节单机8vCPU、16GiB及同机MySQL/Redis等必要服务 |
| 数据集 | 约15,000报价项目、约80GB业务数据和120GB附件 |
| 登录与请求负载 | 50名用户保持在线，常规HTTP请求同时执行最多12个 |
| 后台工作量 | 同时执行2个长任务，最多10个任务排队 |
| 统计口径 | P95按服务端实际处理时长统计，区分正常查询/提交与后台任务受理 |
| 持续时间 | 业务性能混合负载测试连续1小时，长时稳定性测试连续72小时 |

### 6.3 长期运行约束

| 检查项 | 达标条件 |
|---|---|
| 稳定性浸泡 | 在第6.2节负载构成下持续72小时，不能因资源累积被OS杀死 |
| API常驻内存 | 全程≤3GiB；结束时可比较稳态RSS≤起始相同负载水位的110% |
| worker常驻内存 | 总体≤2GiB；完成任务后内存释放至可重复使用水位 |
| 连接和句柄 | 连接≤80、线程≤120、句柄≤4096，且在请求结束后不呈持续增长趋势 |
| 日志与临时文件 | 分别≤20GB与≤30GB，有定期轮转与错误中断清理 |
| 达到上限时 | 拒绝或降级新增任务并记录告警，不使同机数据库不可用 |

### 6.4 恢复要求

| 恢复范围 | RPO最大允许损失 | RTO最长恢复时间 | 实现前提 |
|---|---|---|---|
| 业务数据库和报价审批记录 | **24小时** | **8小时** | 每日完成可恢复备份，离机完整副本可取回并已演练恢复 |
| 原始上传附件与客户输出 | **24小时** | **8小时** | 备份对象同时涵盖文件存储；不只备份MySQL |
| 应用配置与发布版本 | 最新批准版本 | **8小时内一并恢复** | 版本化镜像、配置及必要密钥材料在合法保管位置可恢复 |

## 7. 运维与交付约束

| 能力 | 必须满足 |
|---|---|
| 单机部署 | 镜像、应用、数据库与必要缓存按客户服务器约束运行 |
| 数据升级 | 每次数据库变更可追溯并具备迁移前备份和失败回滚策略 |
| 健康观测 | 监测任务状态、RSS、连接、句柄、磁盘剩余空间以及备份结果 |
| 安全 | 凭据不能入源码仓库；内网/出网仅按已确认策略配置 |
| 交付 | 交付前后端可部署代码、SQL迁移、环境参数样例、运行与恢复说明 |

## 8. 变更和复评边界

| 变化 | 必须重新评估 |
|---|---|
| 改变Java/框架/数据库版本 | 框架兼容、部署与数据库迁移 |
| 服务器CPU/内存/磁盘变化 | 第4章资源预算和第6章性能目标 |
| 数据保留年限或文件增长超出规划 | 存储预算、归档及RPO/RTO |
| 同时请求或长任务并发提高 | API资源、数据库连接、后台worker和负载验收 |
| 人工确认、报价版本与审批原则变化 | 整体架构、数据一致性与权限链路 |
