# 项目基线：约束提取、前置确认与定稿

## 1. 不可突破的定位

**项目基线只定义约束，不写需求，不做设计。** 它限定后续架构、数据库总体、模块设计、实现、测试与部署必须满足什么、不能做什么、在哪种条件下允许变更。

- PRD回答「系统要做什么」；基线回答「后续工程必须遵守什么」；架构回答「用什么组件和交互方式满足约束」。
- 不重述页面、菜单、业务步骤或功能清单；不预先确定组件拓扑、表结构、接口、算法、Worker数量、消息队列选型与线程池配置。
- 禁止把团队开发方法（TDD、Tickets、代码评审、Git流程）写成某个项目的工程基线。
- **从需求可提取的规模、期限、精度、时效、吞吐等信息必须尽量结构化量化**：指标值、单位、范围/对象、起算点或计时边界、适用负载、证据。能由输入准确计算时列出公式和假设。
- 非数值型限制也必须**可判定**：例如禁止重建已有前端风格、不得越权访问、不得把模拟结果标成真实成功。用允许/禁止、是否保留、是否通过的客观判据约束设计，不强行虚构百分比。
- **项目级“明确不做”**指工程禁止事项、系统与第三方的职责边界、既有资产不可修改的范围；PRD中的本期不做功能仍由PRD管理，不复述成基线章节。
- 本Skill只处理首次项目建设前的约束确认。不修改代码、PRD或架构，也不增加研发导航阶段。

### 三个主词（全篇以此为准）

- **台账**：需要**穷尽枚举**的清单——技术栈台账、数据类台账、基础设施台账。判据是「无遗漏」：台账行数 = 材料中实际存在的项数（对照锁文件/构建文件/配置/compose）。
- **落定**：约束已由负责人裁定，可写入正式基线；未裁定的称**未落定**，只允许出现在对话，不得进入正式基线。
- **闭合**：把一类量算到**可与上限比较的总量**（每类小计 → 合计 → 与磁盘/配额比大小），并给出具体余量数值。

## 2. 输入、依据与固定产物

按存在情况读取全部 docs/input/（需求资料、工程资料、环境资料、对接资料及新增目录）；读取PRD、原型设计/页面、客户约束、合同中适用的技术条款；只读检查 code/ 中真实存在的项目文件（前端依赖锁、后端构建文件、现有权限/共享组件、基础设施配置）。不得假定 code/ 子目录名，不以其他项目的示例数字冒充当前事实。

把识别的材料分为：**已落定的硬约束**（已确认需求、合同、负责人裁定的目标）、**核实的现状**（代码与环境中的真实版本/能力，不自动等于未来必须沿用）、**未落定的候选/推荐/未知**（候选、推荐、未知一律只留在对话，未经裁定不得写入正式基线）。

冲突时不静默按某一文档覆盖另一文档；记录冲突及影响并询问。来源必须能追溯，但来源矩阵放在前置确认工作稿，正式基线不堆叠证据过程。

输出（**唯一交付物**）：
- docs/output/01-项目基线/项目基线.md：**正式基线，正文只含已落定约束，零未决值**——不得出现「候选/待定/未定稿/TBD/须经裁定后生效」等字样。

**补齐输入不落盘**：原始输入通常不足以直接生成基线，需先补齐以提高准确率；该补齐在**对话内**完成（预填已知 → 只问缺失/冲突/待裁定 → 用户答），**不产生文件**。未落定的候选/推荐/未知只存在于对话，绝不写入正式基线。

## 3.1 产物契约

**唯一交付物**：`docs/output/01-项目基线/项目基线.md`（正文零未决值），至少包含：
1. **技术/兼容台账（已批准约束与已核实现状分栏）**：语言/运行时、框架、数据库、缓存、消息、调度、对象存储、网关/代理、协议、关键依赖，逐项带真实版本/来源；必须区分“现存依赖/正在运行/正式冻结”，未决定是否采用的技术不可填成既定组件。
2. **数据类台账 + 容量闭合**：每一类持久化数据一行 ×（单条尺寸 × 增长率 × 保留期）→ 小计；仅叠加尚未包含的索引/副本/备份/暂存及安全余量，每项设唯一容量科目ID；日志、附件、备份已计入数据类时不得再次叠加 → 总量与磁盘上限核对，**余量为具体数值**。
3. **基础设施量化**：台账中每个基础设施组件（消息/缓存/调度/对象存储/网关）的吞吐、积压、TTL/保留、重试与死信、资源约束。
4. **部署与网络上限**：整机上限 + **量化余量**（OS预留、中间件开销、备份与安全余量的具体数值）。
5. 性能与恢复、运维交付与变更复评等章节。

生成前的"补齐输入"在**对话内**完成（见 §4.3），用 assets/preconfirmation-template.md 作追问提纲，**不落盘、不交付**。

## 4. 执行流程

### 4.1 全量读取 → 从原始资料抽取约束，而非重写需求

对每条候选信息判断：
- 是否对**项目多个模块、基础工程、部署或验收**形成必须遵守的限制？否则留在PRD或模块设计。
- 是否明确必须/禁止/条件/指标及其检验口径？若只是「支持导出Excel」一类功能需求，不作为基线。
- 是否属于技术实现决策？例如数据库分库方案、队列实现、服务拆分，应交给整体架构。
- 是否必须是**穷尽台账**的一项（某个实际运行组件、某类持久化数据、某个基础设施）？是则进入相应台账。
- 是否是本项目**特殊且不可破坏**的约束，例如原型必须复用、只读第三方数据库、仅有前一天的正式生产数据、某类结果须人工确认后生效。
- 是否明确工程上的**不做/禁止/非本系统责任**，而不是把PRD本期不做功能再列一遍。

从PRD发现的数字要提取为「对象—指标—数值—单位—边界—证据」；例如 N台设备、M秒采样、T年保存或K名用户。已有数值直接预填，不问用户重复填写；缺少采样有效性/来源等影响量化意义的口径时才询问。约束提取结果不等于性能、容量已验证达标。

### 4.2 识别适用维度，自动触发专项

八个核心维度、技术栈台账与组件拓扑之别、条件专项及触发条件见 references/applicability.md；按已有材料识别，允许叠加。要点：
- 每个识别到的**运行组件**进入技术栈台账；
- 每个识别到的**持久化数据类**进入数据类台账；
- 每个识别到的**基础设施**（消息/缓存/调度/对象存储/网关）都要产出自身量化约束。
从材料中发现无法归入固定类别、却会限制整个项目的规则时，增加「项目特有约束」，不可因没有预设栏目而遗漏。

### 4.3 在对话中补齐输入（先预填、只问缺失）

原始输入通常不足以直接生成基线，需先补齐以提高准确率。按 assets/preconfirmation-template.md 组织追问，**在对话内进行、不写文件**：
1. **预填已知**：每项已知约束及其来源先在对话中列清；代码证据只描述现状，并标出「是否必须冻结/允许升级」尚需裁定的情形。
2. **只问缺失**：仅把缺失、冲突、需合同/PM/技术负责人裁定的项摆给用户；每项给选择、数值或「选择+补充」方式；推荐要写前提、理由、代价。
3. **量化换算（AI负责）**：由已确认业务规模与环境推导请求速率/并发、**数据类台账与容量**、中间件指标、后台任务排队与资源目标；明确假设与验证方法，不要求业务用户直接设计线程池、队列、服务部署。
4. **专项与独有约束**：仅就实际触发项追问；禁止事项用明确可通过/不通过判据。

用户只看真正需要回答的条目。高影响问题每轮最多询问3组；已回答或已有依据的不得重复提问。会直接改变工程边界的关键约束未落定时不得生成正式基线。

### 4.4 按裁定结果量化和闭合

- 用户可直接确认业务规模（注册/在线/峰值活跃人数、设备/测点/年数据增长、批处理规模和最长可接受等待）；AI转换为候选请求RPS/并发与工程限制，并交技术负责人确认。**候选值未落定前只留对话。**
- 任务若已由PRD识别，只问任务能力边界：单次数量、最大执行/排队时长、失败允许损失、重复/取消/恢复原则。
- **数据类与容量闭合**：先建数据类台账（每类持久化数据一行），逐类按真实单位计算基础量，明确索引/副本/备份是“本行已包含”还是“独立附加科目”；仅将未计入的独立系统、临时、备份与安全余量加一次，逐科目去重后求总量，与磁盘上限比大小。缺单条尺寸或压缩比时给区间与依据并标注估算，**不得跳过任何数据类**。
- **基础设施量化**：消息/缓存/调度/对象存储/网关的自身指标（吞吐、积压上限、TTL/保留、重试与死信、资源）必须落定。
- **整机余量量化**：给出 OS 预留、中间件与代理开销、备份与快照、安全余量的具体数值，使「各运行单元预算 + 预留 ≤ 整机上限」可核算。具体容器CPU配比、Worker内存及线程数等逐服务分配属于整体架构，不在此决定。
- 可计算指标提供公式、输入参数、单位、峰值系数和不确定性；无可用输入时给区间/方案而非伪精确数字。性能目标须明确 P95/P99 计时边界、负载构成、数据集、测试时长。
- 核查：数据保留×增长与存储上限、目标负载与服务器预算、RPO/RTO与真实备份、权限与数据权威、时效与断线/第三方故障。不能闭合时给出取舍请负责人裁决，禁止静默放宽目标。

### 4.5 输出正式基线及放行

使用 assets/baseline-template.md，正文采用连续章节编号和紧凑表格。只写**已落定、可验证**的项目级约束，以「适用对象/条件—必须或禁止—数值与单位/可判定标准—验证口径」表达；不附资料扫描日志、推荐池或问答过程。

放行前逐条运行 references/checklist.md 的**二进制闸门**（任一为「否」即不得定稿），关键几条：**仅将已批准约束作为正式条目；如仍有影响放行的待裁定项，不得发布 approved 版**、**技术栈台账无遗漏**、**数据类台账每类一行且容量已闭合到具体余量**、**每个基础设施已量化**、**每个量化行有裁定人**。项目经理核准业务/职责边界，技术负责人核准技术/资源/性能等目标；正式通过后才作为整体架构设计的输入。未通过时说明阻塞并给出候选区间、推荐、依据、风险与待裁决人，**不得把部分草稿称为已定稿项目基线**。

## 5. 正面目标与自查反例

正面目标（写出这些即达标）：
- 逐项列出**全部实际运行组件**的技术栈台账，各带版本（来源在对话中核对）。
- 每类持久化数据一行，保留×增长**闭合**到具体余量并与磁盘上限核对。
- 有消息队列就给出吞吐/积压/TTL/重试与死信的量化约束。
- 每个量化行都可判定、有裁定人；正式基线正文零未决值。

反例（硬护栏，避免）：
- ❌「系统包含XX管理、XX审批、XX报表」——这是需求。
- ❌「使用微服务、Kafka、6个Worker，数据库分3张表」——这是设计，除非已由正式工程资料批准为不可更改的硬约束。
- ❌「系统高性能、可用、支持大并发」——缺指标、边界与口径。
- ❌「客户说N人在线，所以必须支持N个同时处理的HTTP请求」——量纲和含义不相同。
- ❌「实现不包括移动端」——普通PRD交付范围，不应仅因“不做”而抄进基线。
- ✅「正式环境禁止公网出站；未经批准不得接入外部AI服务，按网络策略复核」——可判断的禁止边界。
- ✅「必须在已确认资源上支撑约定业务负载，P95≤已裁定的阈值，测试边界明确」——可量化的工程目标。
- ✅「现有前端原型和公共组件不得另建平行体系，允许有限细节调整」——现有工程复用约束。

### 4.7 决策可追溯与审批状态（F07/F08/F23）

正式基线仍仅一份，不新增独立问答稿。每条影响设计/验收的关键约束至少记录 `约束值/客观判据｜证据来源（文件路径及标题或决策链接）｜裁定人｜裁定日期｜批准状态`。**读取到的代码版本是现状，不自动成为“必须使用”的约束**；已批准技术是硬边界；尚在比较的 RabbitMQ/OSS/框架等应交 S04 决策而非提前冻结。模板草稿可标 `draft`/`reviewed`，只有 `approved` 且不存在影响放行的未决项才能存放在正式基线路径供 S04 消费。未触发的技术/中间件不需要伪填版本、吞吐或死信要求。

**容量科目去重示例**：业务数据100GB、附件40GB、运行日志20GB、备份100GB已在互斥科目列出，基础合计为260GB；其后只加“尚未计入的索引、临时、系统与安全余量”，不得再次加40/20/100GB。若某行已经含副本倍率，不得二次加副本；算完标 `已计入科目` 与 `去重检查`。
