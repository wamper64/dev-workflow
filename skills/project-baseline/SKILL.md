# 工程基线生成

## 1. 定位和产物

工程基线规定项目**必须保证什么、允许什么、禁止什么、发生取舍时优先什么**。后续架构、数据库设计、模块开发及验收均需遵守。

- 输入：`docs/input/需求资料/`、`docs/input/工程资料/`、`docs/input/环境资料/`、`docs/input/对接资料/`；现有前端 `code/fld/` 与后端框架 `code/guiwu_ruoyi/` 只用于了解真实约束与可复用能力。
- 输出：`docs/output/01-项目基线/项目基线.md`（若已有唯一项目基线则原位更新）。
- 输入资料中的现状不是天然的目标约束；只有明确指定沿用、已裁定或确属硬性环境边界时才能纳入。
- 不生成工程现状审计、输入证据报告、问题台账、架构实现方案，不修改代码或部署环境。
- 开发方式（TDD、Tickets、代码评审）属于研发规范，**不得写入工程基线正文**。

## 2. 内部执行流程

### 2.1 读取并识别约束

先读 [覆盖检查清单](references/checklist.md)，确认PRD、已有工程资料、目标环境和对接边界。扫描现有代码时只读取必要内容，跳过node_modules、构建产物、缓存、凭据文件。PRD中已包含的原型页面映射不用重建。

内部区分**明确要求、客观硬限制、现有实现、建议和未知**；输出正文不混入分析账本。

### 2.2 提炼第一性原则

从业务错误代价倒推不可接受结果、冲突时的优先级及必要不变量。原则必须能否决错误方案；不能只写“安全可靠”。

### 2.3 确定可执行工程边界

按照 [项目基线正文模板](assets/baseline-template.md) 组织：
1. 业务取舍与建设责任边界。
2. 已裁定技术栈、已有原型和后端框架沿用边界。
3. 目标服务器、网络与部署资源。
4. 规模、请求/任务并发、数据增长与运行期资源上限。
5. 数据一致性、安全权限和保留生命周期。
6. 性能、故障恢复与长期稳定性的**可验收口径**。
7. 交付与升级兼容边界。

**数据库域、分库分表、具体表字段、接口设计**不在这里确定，留给后续对应阶段；已明确裁定的全局技术约束可以记录。

### 2.4 主动补足缺失约束

对输入未明确但会影响架构的事项提出实质推荐，例如服务器容量、数据增长、资源稳定性、恢复目标。问题必须包含：缺口及影响、推荐值或方向、理由和前提、代价/备选方案。

- 可由现有资料直接推算的数量级，说明口径后推导。
- 涉及业务取舍、SLA、保留期或成本承诺的事项，获得用户确认后方可定稿。
- 现实硬事实须通过资料或实际环境核实；**不能把推荐服务器规格写成真实服务器配置**。
- 每轮最多询问 **3 个高影响问题**，优先阻塞架构设计的事项。
- 不重复询问已经明确的PRD、约定或用户答复。
- 有依赖未确认时先完成可确定的正文，问题留在会话；沉默不视为采纳。

### 2.5 一致性与可读性检查

依次读取 [约束一致性检查](references/consistency.md)、[表述规范](references/editorial-standard.md)。
- 核查容量预算与目标服务器资源能闭合；保留期与修订依据的追溯能闭合。
- 测试目标的环境、数据、负载、时间口径不丢失；不得把50个在线用户改成50个请求并发。
- 禁止修改第三方接口承诺、身份来源或RPO/RTO等已确定边界。
- 正文带连续章节编号（1、1.1），同类规则用紧凑表格，删除空章节、长篇证据、草案状态和核心约束摘要。
- 生成后做两遍审查：首先审查能否约束架构设计，再审查决策是否快速可读。

## 3. 决策和交付

若关键约束尚待裁定，给出**推荐方案与最多3个问题**，继续整理已能确定的部分。不能将未确认事项写成硬性条款，也不能称为完整可用基线。

交付时给出文档位置、已可用的约束要点及会影响后续设计的未决事项。需要更新时保留原来仍有效的裁定，只修改确有新依据的内容，不在基线正文添加变更或证据台账。
