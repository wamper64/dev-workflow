# 项目基线：约束提取、前置确认与定稿

## 1. 不可突破的定位

**项目基线只定义约束，不写需求，不做设计。** 它限定后续架构、数据库总体、模块设计、实现、测试与部署必须满足什么、不能做什么、在哪种条件下允许变更。

- PRD回答「系统要做什么」；基线回答「后续工程必须遵守什么」；架构回答「用什么组件和交互方式满足约束」。
- 不重述页面、菜单、业务步骤或功能清单；不预先确定组件拓扑、表结构、接口、算法、Worker数量、消息队列选型与线程池配置。
- 禁止把团队开发方法（TDD、Tickets、代码评审、Git流程）写成某个项目的工程基线。
- **从需求可提取的规模、期限、精度、时效、吞吐等信息必须尽量结构化量化**：指标值、单位、范围/对象、起算点或计时边界、适用负载、证据。能由输入准确计算时列出公式和假设；缺变量时不编造结果。
- 非数值型限制也必须**可判定**：例如禁止重建已有前端风格、不得越权访问、不得把模拟结果标成真实成功。用允许/禁止、是否保留、是否通过的客观判据约束设计，不强行虚构百分比。
- **项目级“明确不做”**指工程禁止事项、系统与第三方的职责边界、既有资产不可修改的范围；PRD中的本期不做功能仍由PRD管理，不复述成基线章节。
- 本Skill只处理首次项目建设前的约束确认。不修改代码、PRD或架构，也不增加研发导航阶段。

## 2. 输入、依据与固定产物

按存在情况读取全部 docs/input/（需求资料、工程资料、环境资料、对接资料及新增目录）；读取PRD、原型设计/页面、客户约束、合同中适用的技术条款；只读检查 code/ 中真实存在的项目文件（前端依赖锁、后端构建文件、现有权限/共享组件、基础设施配置）。不得假定 code/ 子目录名，不以其他项目的示例数字冒充当前事实。

把识别的材料分为：
1. **已批准的硬约束**：已确认需求、合同、负责人裁定的目标。
2. **核实的现状**：代码和环境中的真实版本/能力；现状不自动等于未来必须沿用。
3. **可推导候选**：有明确输入、公式、假设的容量或并发估计；须经相应负责人裁定后才成为硬约束。
4. **推荐或未知**：基于经验提出候选、适用前提及代价，绝不默认为已确认。

冲突时不静默按某一文档覆盖另一文档；记录冲突及影响并询问。来源必须能追溯，但来源矩阵放在前置确认工作稿，正式基线不堆叠证据过程。

输出：
- docs/output/01-项目基线/项目基线前置约束确认表.md：自动预填的**项目专用工作稿**，记录已知依据、未裁定约束、建议、用户答复与裁定；只让用户填写缺失/冲突/确需裁定项。
- docs/output/01-项目基线/项目基线.md：只包含通过确认的**正式约束**，不含提问、方案待选和项目需求清单。

## 4. 执行流程

### 4.1 全量读取 → 从原始资料抽取约束，而非重写需求

对每条候选信息判断：
- 是否对**项目多个模块、基础工程、部署或验收**形成必须遵守的限制？否则留在PRD或模块设计。
- 是否明确必须/禁止/条件/指标及其检验口径？若只是「支持导出Excel」一类功能需求，不作为基线。
- 是否属于技术实现决策？例如数据库分库方案、队列实现、服务拆分，应交给整体架构。
- 是否是本项目**特殊且不可破坏**的约束，例如原型必须复用、只读第三方数据库、仅有前一天的正式生产数据、某类结果须人工确认后生效。
- 是否明确工程上的**不做/禁止/非本系统责任**，而不是把PRD本期不做功能再列一遍。

从PRD发现的数字要提取为「对象—指标—数值—单位—边界—证据」；例：N台设备、M秒采样、T年保存或K名用户。已有数值直接预填，不问用户重复填写；缺少采样有效性/来源等影响量化意义的口径时才询问。约束提取结果不等于性能、容量已验证达标。

### 4.2 识别适用维度，自动触发专项

**默认核心**：工程原则与取舍、工程禁止及责任边界、技术及既有工程兼容、运行与网络边界、业务规模与资源、数据安全与生命周期、性能稳定与恢复、运维交付。

**条件专项**按已有材料识别，允许叠加：IoT设备接入、关键计算与计量、第三方对接、后台异步长任务、定时任务、业务审批、Agent工具调用、远程控制、多租户、信创特殊合规。能源只是业务领域，不应成为所有项目必填类别；长任务、定时任务和审批不能混成一类。不满足触发条件时不问、不写无关章节。

从材料中发现无法归入固定类别、却会限制整个项目的规则时，必须增加「项目特有约束」，不可因没有预设栏目而遗漏。

### 4.3 生成项目专用的前置约束确认表

先按照 assets/preconfirmation-template.md 建工作稿：
1. **自动预填区**：每项已知硬约束及其来源；代码证据只描述现状，并单独标出「是否必须冻结/允许升级」尚需裁定的情形。
2. **只需用户处理的清单**：未知、资料冲突、需要合同/PM/技术负责人裁定的关键项；每项提供选择、数值输入或「选择+补充」方式；可选推荐要写前提、理由、代价。
3. **量化换算区（AI负责）**：由已确认业务规模和已核实环境推导HTTP请求速率/并发、容量增长、后台任务排队及资源目标；明确假设和验证方法，不能要求业务用户直接设计线程池、队列、服务部署。
4. **专项与独有约束**：仅输出实际触发的内容；对禁止事项使用明确可通过/不通过的判据。

用户只看真正需要回答的条目。高影响问题每轮最多询问3组，允许一次在表内补答多项；回填后自动更新已有确认项，禁止重复提问。对暂时无法确定且非关键的条目，可记录为后续需确认；**会直接改变工程边界的关键约束未裁定时不得放行正式基线**。

### 4.4 按裁定结果量化和闭合

- 用户可直接确认业务规模（注册/在线/峰值活跃人数、设备/测点/年数据增长、批处理规模和最长可接受等待）；AI转换为候选请求RPS/并发与工程限制，并交技术负责人确认。
- 任务若已由PRD识别，只问任务能力边界：单次数量、最大执行/排队时长、失败允许损失、重复/取消/恢复原则；不重新询问要开发哪些任务。普通导出、后台异步、定时和审批分别判断。
- 可计算指标提供公式、输入参数、单位、峰值系数和不确定性；不存在可用输入时给区间/方案而非伪精确数字。验证性能目标要明确P95/P99计时边界、负载构成、数据集、测试时长。
- 基线确定**部署资源上限及余量、目标负载和约束**；具体容器CPU配比、MySQL/Worker内存及线程数等分配属于整体架构。架构完成后须证明总预算闭合，不能在项目基线未有组件设计时伪装已完成逐服务预算。
- 核查数据保留×增长与存储上限、目标负载与服务器预算、RPO/RTO与真实备份条件、权限与数据权威、时效与断线/第三方故障的兼容性。不能闭合时给出取舍请负责人裁决，禁止静默放宽目标。

### 4.5 输出正式基线及放行

使用 assets/baseline-template.md，正文采用连续章节编号和紧凑表格。只写已确认、可验证的项目级约束，并用「适用对象/条件—必须或禁止—数值与单位/可判定标准—验证口径」表达；不附资料扫描日志、推荐池或问答过程。

运行 references/checklist.md 的六项关卡：覆盖、约束明确、可量化/可判定、前后一致、未越设计边界、关键值已裁定。项目经理核准业务/职责边界，技术负责人核准技术/资源/性能等目标；正式通过后才作为整体架构设计的输入。未通过时可交付前置确认表和已确认部分，但不得把部分草稿称为已定稿项目基线。

## 5. 禁止事项与自查反例

- ❌「系统包含XX管理、XX审批、XX报表」——这是需求。
- ❌「使用微服务、Kafka、6个Worker，数据库分3张表」——这是设计，除非相关选择已由正式工程资料批准为不可更改的硬约束。
- ❌「系统高性能、可用、支持大并发」——缺指标、边界与口径。
- ❌「客户说50人在线，所以必须支持50个同时处理的HTTP请求」——量纲和含义不相同。
- ❌「实现不包括移动端」——普通PRD交付范围，不应仅因“不做”而抄进基线。
- ✅「正式环境禁止公网出站；未经批准不得接入外部AI服务，按网络策略复核」——可判断的禁止边界。
- ✅「必须在已确认资源上支撑约定业务负载，P95≤经裁定的阈值，测试边界明确」——可量化的工程目标。
- ✅「现有前端原型和公共组件不得另建平行体系，允许有限细节调整」——现有工程复用约束。
