# 工程基线生成

## 1. 定位与边界

这是后续整体架构、数据库总体、模块开发、测试与部署的**全局工程约束**，不是PRD复述、架构实施方案或代码现状审计。每项关键约束应当能判断某种方案是否合格。

输入：`docs/input/需求资料/`、`docs/input/工程资料/`、`docs/input/环境资料/`、`docs/input/对接资料/`，按需只读`code/` 中现有前后端工程的真实版本与可复用边界。输出：`docs/output/01-项目基线/项目基线.md`。

不重复生成PRD已有页面映射，不制定各模块的表字段、详细接口或实现类；TDD、Tickets、代码评审属于研发方式，不写进工程基线正文。

## 2. 必读检查文件

依次读取 [覆盖检查](references/checklist.md)、[数值与预算规则](references/quantification-standard.md)、[一致性检查](references/consistency.md)、[表达规范](references/editorial-standard.md)、[正文模板](assets/baseline-template.md)。

## 3. 工作流程

### 3.1 识别事实、裁定、建议和未知

读取确认PRD和工程/环境/对接资料，核对已有前后端工程的技术、版本、真实运行约束，区分：已明确裁定、可核实硬事实、可计算推导、待确认推荐、完全未知。

“代码里有Redis”不等于“目标必须部署Redis”；“现有Java8”不能自动覆盖已经裁定的Java17。已有PRD和用户答复优先，不照搬其他项目资源参数。

### 3.2 提炼第一性原则和**有数值的**项目约束

按 `references/quantification-standard.md` 逐项生成：
1. **统一技术栈**：前端框架、构建工具、UI组件库、项目真实后端语言/框架、数据库/中间件/工作流适用项的名称和版本，复用与变更边界。
2. **部署资源**：CPU架构与核数、内存总量与可用量、磁盘容量与类型、OS版本、网络、Docker/扩容限制。
3. **资源分配**：CPU按服务配额/预算，内存按OS、MySQL、业务API、后台任务、缓存、代理和余量分项GiB，磁盘按OS/数据库/附件/日志/临时/备份/余量分项GB，数值合计闭合。
4. **业务负载**：在线人数、同时执行HTTP请求、后台任务执行并发、队列容量、任务执行/排队含义分别定值。
5. **数据生命周期**：核心业务记录、业务确认版本、历史明细、审批审计（如有）、附件、系统日志逐项写“保留N年/月”和起算点，引用关系与保留期闭合。
6. **性能和稳定性**：主要操作P95阈值、错误率或成功率、负载数据集和测试时间；常驻内存RSS、线程/连接/句柄、磁盘文件上限、浸泡时长和回归阈值。
7. **恢复**：RPO、RTO、备份频率、恢复对象及依赖的介质/网络条件。
8. **业务与安全原则**：取舍优先级、确认/审批/业务版本不变量、权限和第三方故障边界。

不得只写“长期保存”“容量有余量”“保证高性能”等概念性规则，或用模板空白占位来逃避必须确定的指标。

### 3.3 对缺项提出**具体数字的推荐**并询问

缺少工程上必须确定的值时，主动按业务量、部署条件和风险给出候选数值（含单位、适用前提和成本/替代方案），**每轮最多询问3个高影响问题**。优先询问：
- 目标服务器CPU、内存、磁盘与可扩容性（硬件真实事实，不可猜）。
- 数据保留年限/年增长量及RPO/RTO（业务承诺，用户裁定）。
- HTTP请求、后台任务并发及主要操作P95目标（与用户在线量分开）。

允许在用户明确授权范围内独立定目标；其余必须获得答复才能把推荐写为硬约束。当前无法确定时可先生成已确定章节，在会话报告阻塞，**不得声称完整基线已定稿**。问题/备选项不要写进正式工程基线正文。

### 3.4 资源、保留和验收**闭合验证**

内部逐项核算：
- CPU所有分项及OS预留与服务器核数兼容；超分配要明确获批准。
- RAM：OS/数据库/API/worker/缓存/代理和安全余量之和≤目标物理可用内存。
- 磁盘：系统镜像+业务数据与索引+附件+日志+临时+本地备份+剩余空间≤磁盘可分配容量。异机备份不能冒充本机已有功能。
- 数据量：年增长×保留年限及起始存量与文件/数据库预算相容；未给行大小不得虚构精确容量。
- P95：服务端计时边界、请求并发、测试数据量、持续时长一致；在线人数≠并发请求，排队≠执行。
- 版本、审批及附件数据保存起算点互相兼容；恢复对象和RPO/RTO与备份方式一致。

不闭合先在会话提出扩容、修改性能/年限或改变架构的方案，**不得静默放宽任何已确认约束**。

### 3.5 输出及验收关卡

基于 `assets/baseline-template.md` 写干净的中文正文，连续章节编号，紧凑表格分行呈现具体规则和单位。不要生成“核心约束摘要”、分析证据、代码盘点、状态/待确认列和冗余过程说明。

最终必须审查：技术栈是否具体、关键数值是否完整并已裁定、各分项资源是否闭合、数据保留年限及起算点是否确定、并发口径/性能/P95是否明确、长时运行与RPO/RTO是否可验收，且约束确实能否决不适合的架构。

未通过者只能交付“已确定部分+会话中的推荐与待裁定问题”，**不能标为已完成项目基线**。
