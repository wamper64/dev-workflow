# 报价项目：自动提取与前置约束确认演示

> 全部为**模拟示范，不是该报价项目真实输入、负责人答复或已确定指标**。其他项目不能直接沿用这些数字。

## 第一步：从已有资料提取，不重新调查功能

假设已确认PRD和原型可以核实：
- 有现成前端原型和后端框架；项目要求继续复用，不重做前端视觉体系。
- 存在人工确认后正式生效的业务结果、报价版本和权限边界。
- 输入材料假设有「50名用户保持在线」目标，但**没有**同时HTTP请求数。
- 目标服务器、存储保留年限和恢复承诺仍未知。

Skill自动写入前置表的事实（**若能从真实输入得到才可写**）：

| 约束 | 自动预填依据 | 是否需重复询问 |
|---|---|---|
| 原型视觉和既有框架不可平行重做 | 已确认PRD/工程约定及真实code/ | 否 |
| 已经确认的正式版本不能被自动结果静默覆盖 | 已批准业务规则 | 否 |
| 50人在线 | 示例PRD目标，人数/含义明确 | 否 |
| 同时HTTP请求量 | 未知，50在线无法直接推断 | 需确认业务使用规律再推导 |

注意：PRD里存在审批功能，是识别审批相关**工程约束**的证据；不能在基线里重新规定审批节点。

## 第二步：用户只看到未决约束

| 待确认项 | 选项/输入 | AI提供的说明 |
|---|---|---|
| 目标服务器与出网边界 | CPU____核，内存____GiB，磁盘____GB；出网禁止/白名单/允许 | 若客户未提供真实规格，可提出目标硬件方案，但不得写为现有资源 |
| 数据保留和起算点 | 报价/审计/附件各____年，起算点____ | 推荐要同时考虑依赖关系、容量和合规成本 |
| 50在线的使用高峰是什么样 | 高峰活跃____人，操作频率____次/分钟，单次操作约____个请求（能观察则自动提取） | AI据此计算平均/峰值RPS和HTTP请求并发候选 |

每轮优先询问最多三组高影响问题，已经从输入得知的无需再问。

## 第三步：由AI换算工程候选，并区分执行与排队

仅作计算说明：假设负责人确认高峰有10人持续操作，每人每分钟3次，每次平均2个API请求，则候选平均请求速率 = 10×3×2/60 = **1 RPS**。若计划按3倍短时峰值覆盖，候选为 **3 RPS**，仍需要真实交互模式、自动轮询和性能测试验证。在线50人**不代表**50个并发HTTP请求。

如果已确定有长任务，业务人员确认「单次处理规模、最多同时发起数、包含排队的最长等待时间、重复/失败边界」，AI才提出执行并发与队列上限候选。不能问业务人员要设几个Worker或选哪个队列。

## 第四步：获得裁定后才能定稿

技术负责人需要确认：
- 真实目标硬件/网络与整机资源余量是否足够；逐服务预算在下一步架构中闭合。
- 服务端P95目标与负载/数据集、任务等候/执行、稳定性验证条件。
- 数据/附件/配置的RPO、RTO与真实备份介质可用性。

正式「项目基线.md」只收录**已确认、可量化或可判定**的工程限制和项目特殊禁止项，不写本期不做功能或具体技术设计。未裁定的关键约束留在「项目基线前置约束确认表.md」，明确阻塞，不宣称已定稿。
