# 报价项目：工程基线缺少数字时，Skill 应如何运行

> **模拟会话**。它展示正确的补全过程，不表示本项目实际已经回答这些问题。示例中的所有数值必须经项目负责人确认或获得明确的自主裁定授权，才能写入正式工程基线。

## 输入与已知边界

- 已确认PRD和已有前端原型（保持样式）、若依后台框架。
- 有报价、计算单、需求解析、人工核对、审批和归档需求。
- 服务器环境、技术具体版本、数据保留、HTTP并发、性能和RPO/RTO缺少足够明确的当前项目裁定。

## 第一轮：3组最高影响的问题

**问题1：正式目标服务器的具体配置及备份条件？**

- 缺口：CPU/内存/磁盘和离机备份目的地没有核实。
- 候选目标：8 vCPU / 16 GiB / 500 GB SSD，Ubuntu 22.04 单机容器部署；另配置离机恢复介质。
- 理由：适用于假设50在线、少量后台任务且同机部署数据库的小型场景。该值不是根据现有报价PRD推算出的事实，需要结合实际容量再评估。
- 备选代价：若是4C8G，必须降低并发预算或拆服务；若没有离机存储，无法承诺示例RPO/RTO。
- 请确认：真实已有硬件和网络，还是接受候选目标配置？

**问题2：报价、参数版本、计算依据、审批和附件究竟保存几年？**

- 候选方案A：关联的全部报价业务数据从项目最终归档或终止日起**5年**，普通应用运行日志保存**180天**。
- 候选方案B：业务数据保留3年，空间和迁移成本更低，但可能不足以覆盖客户追溯/合同要求。
- 注意：审批/附件不能比其仍被引用的报价版本提前清除。
- 请确认：业务与合规要求、具体起算点和可否到期清理？

**问题3：50在线用户对应多少正在处理的HTTP请求和后台任务？**

- 候选：50人保持登录，常规HTTP同时请求12个，后台解析/计算任务2个并行、最多排队10个，长任务最长执行20分钟（不包含排队）。
- 理由：HTTP请求并发与在线人数不同，2个后台任务只是需要验证资源预算的候选值。
- 请确认：典型峰值和业务峰值持续时间是否支持该估计？

### 假设用户选择了上述具体方案

仅在**已收到明确确认**之后，Skill 才能把8C16G500GB、5年/180天、12 HTTP/2后台/队列10写进目标基线。

## 第二轮：进一步完成性能和恢复约束

**问题1：统一技术栈的实际版本和升级边界？**

推荐沿用 code/fld、code/guiwu_ruoyi 已锁定的版本；检查 package.json、pom.xml 和现有运行环境，不能把技术示例里的 Vue 3.5、Java 8、Spring Boot 2.7、MySQL 8.0 等默认成真实代码版本。

**问题2：性能目标如何裁定？**

- 候选：12个常规HTTP并发、约15,000报价项目条件下，项目列表 P95≤2.0秒、详情≤1.5秒、保存≤3.0秒；后台任务受理返回≤1.5秒。
- 计时：从服务端接收请求至完成响应；不包含后台长任务本体。
- 业务错误率候选≤0.5%。客户须确认是否符合期望，再由后续性能测试验证。

**问题3：RPO/RTO与持续运行验收目标？**

- 候选：离机每日备份，数据库+附件RPO≤24小时，系统及业务数据RTO≤8小时；完整恢复依赖离机介质真实可用。
- 运行稳定性候选：72小时浸泡，API RSS≤3GiB，结束回到起始相同负载水位的110%以内；数据库连接≤80、线程≤120、句柄≤4096。
- 若离机备份没有落实，就不能承诺这一组恢复目标。
