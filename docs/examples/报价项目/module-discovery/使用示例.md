# 业务模块拆分 · 报价系统使用示例

> 示例业务能力不代表项目真实PRD已覆盖，也不预设模块数量。

## 输入与拆分依据

读取 `docs/input/需求资料/` 已确认的角色×核心场景、原型页面，S03项目约束、S04批准组件与链路、S05核心表/字段/ER及权威Owner，以及真实 `code/`。

1. **场景发现**：从业务角色、触发入口、核心对象/状态变化及可观察结果形成候选业务能力。
2. **职责/生命周期拆合**：依据同一业务目标、核心对象生命周期、规则与维护责任决定合并/分离；避免按菜单、页面或Controller机械拆。
3. **架构/Owner核验**：核对模块不跨越已冻结组件、数据写权威和现有原型复用限制；每个场景有一个主责模块。
4. **依赖DAG**：区分上游必须实际交付的强阻塞、契约可先并行的关系，以及设备/第三方/环境阻塞。
5. **补删改与审核**：漏业务场景补、无依据功能删、跨模块Owner/依赖冲突改；项目经理确认业务、技术总监确认架构。

## 示例判定

例如“告警规则配置、告警事件产生、告警确认/关闭”虽可分属多个菜单，但若共同管理同一告警对象生命周期，优先按同一模块聚合；报价业务中的“需求解析”与“报价审批”是否独立，则以实际业务对象、状态Owner、可分别验收及依赖为依据。

**输出**：
- `docs/output/05-模块拆分/项目模块清单.md`
- `docs/output/05-模块拆分/模块依赖关系.md`
- S07审核在对话和两份正式清单中体现，不生成独立的模块拆分审核.md

S07仅形成业务模块池，**S09**再选择本轮真实就绪任务与做详细设计，S11使用Matt原版to-tickets拆实现级任务。
